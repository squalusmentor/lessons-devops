# Урок 10. Бэкап по расписанию, лимиты по метрикам, редеплой

Весь урок разобран на живом проекте: Telegram-бот, API на Go и MongoDB на одной виртуалке с 1 vCPU и 2 ГБ RAM. Стек катится плейбуком из пайплайна, как в уроке 9. За два дня там закрыли три дыры:

| Было | Чем грозило | Что сделали |
|---|---|---|
| дамп базы только перед деплоем | деплои ручные и редкие, между ними данные живут без копии | контейнер, который раз в сутки кладёт дамп в S3, старые копии S3 удаляет сам |
| лимиты памяти и CPU стоят на глаз | одним контейнерам выдано лишнее, монга упирается в потолок CPU | лимиты пересчитаны по данным Netdata за 6 суток |
| деплой упал, прод лежит | роль `deploy` уже остановила стек, поднимать его некому | при падении сам запускается редеплой с последнего удачного тега, при успехе выпускается новый тег |

База в проекте MongoDB, у тебя Postgres. Это сделано нарочно: решения переносятся, команды нет, и в практике их придётся найти самому

## 2. Бэкап по расписанию

### Контейнер, который спит

```yaml
  ec-mongo-backup:
    build: ./scripts/mongo-backup
    image: ec-mongo-backup:local
    container_name: ec-mongo-backup
    environment:
      - "BACKUP_CRON=${BACKUP_CRON:-0 3 * * *}"
      - TZ=Europe/Moscow
      - MONGODB_URI=mongodb://ec-mongodb:27017
      - S3_HOSTNAME=${S3_HOSTNAME:-ams1.vultrobjects.com}
      - S3_ACCESS_KEY=${S3_ACCESS_KEY}
      - S3_SECRET_KEY=${S3_SECRET_KEY}
      - S3_BUCKET_NAME=${S3_MONGO_BACKUP_BUCKET_NAME:-mongo-backup}
      - S3_FILE_PATH=${S3_MONGO_BACKUP_REGULAR:-regular}
    mem_limit: 128m
    mem_reservation: 16m
    cpus: 0.1
    restart: unless-stopped
    networks:
      - ec-network
    depends_on:
      ec-mongodb:
        condition: service_healthy
```

Внутри маленькая программа на Go. Она читает расписание, считает время следующего запуска и спит до него. В нужный момент запускает штатный `mongodump` и заливает архив в S3. Суть кода:

```go
for {
    next := schedule.Next(time.Now())
    log.Printf("следующий бэкап: %s", next.Format(time.RFC3339))

    select {
    case <-ctx.Done(): // docker stop: выходим сразу, не дожидаясь утра
        return
    case <-time.After(time.Until(next)):
    }

    // Падение бэкапа не роняет контейнер: следующая попытка по расписанию
    if err := backup(ctx, s3, mongoURI, bucket, dir); err != nil {
        log.Printf("бэкап не удался: %v", err)
    }
}
```

```go
// Сначала файл, потом загрузка: оборванный mongodump в S3 не попадёт
dump := exec.CommandContext(ctx, "mongodump", "--uri="+mongoURI, "--archive="+tmp, "--gzip", "--quiet")
if err := dump.Run(); err != nil {
    return fmt.Errorf("mongodump: %w", err)
}
info, err := s3.FPutObject(ctx, bucket, key, tmp, minio.PutObjectOptions{})
```

Архив ложится в `s3://mongo-backup/regular/encon-20261006T000000.gz`, рядом с дампами перед деплоем из `before-update/`, в том же формате

### Решения и почему

| Решение | Почему |
|---|---|
| бэкап отдельным сервисом в том же compose | выкатывается тем же плейбуком, что и база, логи в `docker logs`, лимиты как у всех |
| Go и сон до следующего запуска | контейнер почти всё время спит. Go-процесс в простое берёт 8 МБ и ноль CPU, опросов «не пора ли» нет |
| дамп делает `mongodump`, а не свой код | формат архива совместим с `mongorestore` и с дампом перед деплоем |
| расписание строкой `BACKUP_CRON`, пять полей | привычный синтаксис cron. Для проверки ставится `*/2 * * * *`, для прода дефолт `0 3 * * *` |
| `TZ=Europe/Moscow` | пользователи русскоязычные, «ночь» считается по Москве |
| сначала временный файл, потом загрузка | при потоке прямо в S3 оборванный дамп остался бы в бакете усечённым архивом, который выглядит как нормальный бэкап |
| сбой только в лог, контейнер живёт | следующая попытка через сутки. Цена: о сбое никто не узнает, пока не посмотрит логи |
| образ собирается на VM из `build:` | бинарник крошечный, отдельный пайплайн сборки ради него не заводили |
| в образе из `mongodb-tools` оставлен один `mongodump` | остальные утилиты весят около 70 МБ, итоговый образ 47 МБ |
| `mem_limit: 128m` | на 64m `mongodump` убивало по OOM уже на базе 75 МБ, пик был 56 МиБ |

Из-за `build:` в роли деплоя `docker compose up -d` превратился в `up -d --build`. Без флага compose видит, что образ `ec-mongo-backup:local` уже есть, и правки кода молча не подхватываются

### Восстановление

Бэкап, из которого ни разу не восстанавливались, это надежда. В проекте восстановление проверено на чистой монге: `users=3`, `messages=150001`, как в источнике. Команды на сервере:

```bash
docker run --rm -v "$PWD":/dl \
  -e RCLONE_CONFIG_S3_TYPE=s3 -e RCLONE_CONFIG_S3_PROVIDER=Other \
  -e RCLONE_CONFIG_S3_ACCESS_KEY_ID=<S3_ACCESS_KEY> -e RCLONE_CONFIG_S3_SECRET_ACCESS_KEY=<S3_SECRET_KEY> \
  -e RCLONE_CONFIG_S3_ENDPOINT=https://ams1.vultrobjects.com \
  rclone/rclone:1.75.1 copyto s3:mongo-backup/regular/<файл>.gz /dl/<файл>.gz

docker cp <файл>.gz ec-mongodb:/backup/
docker exec ec-mongodb mongorestore --archive=/backup/<файл>.gz --gzip --drop
docker exec ec-mongodb rm /backup/<файл>.gz
```

`rclone` запускается так же, как в разделе 3. `--drop` удаляет коллекцию перед восстановлением. Без него архив ложится поверх текущих данных: документы с теми же `_id` пропускаются, лишние остаются

Ротации в коде контейнера нет: старые копии удаляет сам S3, правило разобрано в разделе 3

## 3. S3: стандарт и бакет проекта

В уроке 6 S3 мелькнул одной строкой: бакет, файлы по именам, пара ключей. Здесь на нём держатся все бэкапы, поэтому подробнее

### Что такое S3

S3 (Simple Storage Service) это объектное хранилище Amazon. Его HTTP API стал стандартом: Vultr, MinIO, Yandex Object Storage, Selectel, Cloudflare R2 повторяют тот же API. Отсюда главное следствие: клиенты общие. `aws` CLI, `s3cmd`, `rclone`, `boto3`, `minio-go` работают с любым из них, меняются только endpoint и ключи

Совместимость при этом неполная. У каждого провайдера есть таблица, какие части API он поддерживает. У Vultr это [S3 Compatibility Matrix](https://docs.vultr.com/products/storage/object-storage/s3-compatibility-matrix), и на ней проект споткнулся, об этом ниже в ротации

### Бакет, объект, ключ

| Понятие | Что это |
|---|---|
| бакет | контейнер верхнего уровня. У него имя и свои настройки: lifecycle-правила, доступ |
| объект | файл плюс метаданные: размер, дата, тип. Дописать или поправить объект нельзя, только заменить целиком |
| ключ | полное имя объекта в бакете: `regular/encon-20261006T000000.gz` |
| префикс | начало ключа. Папок в S3 нет, `regular/` это общее начало у ключей, панели и клиенты просто рисуют его папкой |

Отсутствие папок видно в живом бакете. До первого ночного бэкапа в `regular/` лежал один объект с ключом `regular/` размером 0 байт. Это маркер, который создаёт панель, когда «создаёшь папку». Он ничему не мешает

### Каждое действие это HTTP-запрос

| Действие | Запрос |
|---|---|
| положить файл | `PUT /<бакет>/<ключ>` |
| скачать | `GET /<бакет>/<ключ>` |
| список по префиксу | `GET /<бакет>?list-type=2&prefix=regular/` |
| удалить | `DELETE /<бакет>/<ключ>` |
| поставить lifecycle-правила | `PUT /<бакет>?lifecycle`, правила XML в теле |
| прочитать lifecycle-правила | `GET /<бакет>?lifecycle` |

Каждый запрос подписан ключами по схеме SigV4. Access key это имя ключа, оно идёт в запросе открыто. Secret key по сети не передаётся: клиент считает им подпись запроса, сервер считает свою и сравнивает. Подписывать руками не нужно, это делает любой клиент из списка выше. Поэтому `\r` на конце ключа из урока 8 ломал всё: клиент честно отправлял ключ с лишним символом, и сервер такого не находил

Адрес бакета бывает двух видов:

| Стиль | Адрес |
|---|---|
| path-style | `https://ams1.vultrobjects.com/mongo-backup/regular/...` |
| virtual-hosted | `https://mongo-backup.ams1.vultrobjects.com/regular/...` |

Отсюда у `s3cmd` два параметра: `--host` это endpoint, `--host-bucket` шаблон адреса с бакетом в имени хоста. `ams1` в endpoint это регион, Амстердам

### Что лежит в хранилище проекта

| Бакет и префикс | Кто пишет | Когда | Сколько живёт |
|---|---|---|---|
| `mongo-backup/before-update/` | роль `deploy` через `rclone` | перед каждым деплоем | без срока |
| `mongo-backup/regular/` | `ec-mongo-backup` через `minio-go` | каждую ночь в 03:00 по Москве | 60 дней |
| `mask-profile-pics/base-images/` | `api` | при загрузке фото маски | это данные приложения, без срока |

Что происходит в `mongo-backup` за сутки. В 03:00 по Москве, это 00:00 UTC, в `regular/` появляется новый архив. Раз в сутки, тоже в 00:00 UTC, Vultr проходит по lifecycle-правилам и удаляет из `regular/` всё старше 60 дней. В установившемся режиме там около 60 архивов, по одному на ночь. `before-update/` прирастает на архив с каждым деплоем, и его никто не чистит

Ключ на всё хранилище один: те же `S3_ACCESS_KEY` и `S3_SECRET_KEY` получают `api`, бэкап и ansible. Настраивать проще, но тот, кто вытащит ключи из `api`, сможет стереть и бэкапы

### Посмотреть, что в бакете

```bash
docker run --rm \
  -e RCLONE_CONFIG_S3_TYPE=s3 -e RCLONE_CONFIG_S3_PROVIDER=Other \
  -e RCLONE_CONFIG_S3_ACCESS_KEY_ID=<S3_ACCESS_KEY> -e RCLONE_CONFIG_S3_SECRET_ACCESS_KEY=<S3_SECRET_KEY> \
  -e RCLONE_CONFIG_S3_ENDPOINT=https://ams1.vultrobjects.com \
  rclone/rclone:1.75.1 lsl s3:mongo-backup/regular/
```

| Что | Зачем |
|---|---|
| `rclone` в контейнере | на сервере ничего не ставится. Тот же образ роль деплоя использует для заливки дампа перед обновлением |
| `RCLONE_CONFIG_S3_*` | конфиг rclone целиком из переменных, файл конфига не нужен. `S3` в имени переменных это имя удалённого хранилища, отсюда `s3:` в пути |
| `PROVIDER=Other` | хранилище не Amazon, rclone не подставляет ничего специфичного для AWS |
| `lsl` | список объектов по префиксу с размером и датой |

### Ротация: S3 чистит сам

Копии в `regular/` старше 60 дней удаляет сам S3 lifecycle-правилом. Это настройка бакета, кода для неё нет ни в контейнере, ни в пайплайне

```xml
<LifecycleConfiguration>
  <Rule>
    <ID>expire-regular-backups</ID>
    <Filter><Prefix>regular/</Prefix></Filter>
    <Status>Enabled</Status>
    <Expiration><Days>60</Days></Expiration>
  </Rule>
</LifecycleConfiguration>
```

| Поле | Что значит |
|---|---|
| `ID` | имя правила. По нему правило находят и заменяют, повторно оно не добавляется |
| `Filter` и `Prefix` | к каким ключам применяется. Дампы перед деплоем в `before-update/` правило не трогает |
| `Status` | `Disabled` выключает правило без удаления |
| `Expiration` и `Days` | объекты старше 60 дней от даты загрузки удаляются |

Так правило выглядит в документации Vultr ([Security best practices](https://docs.vultr.com/platform/security-best-practices/vultr-object-storage)), там же команда:

```bash
s3cmd setlifecycle lifecycle.xml s3://mongo-backup \
  --host=ams1.vultrobjects.com \
  --host-bucket="%(bucket)s.ams1.vultrobjects.com"
```

Прочитать текущие правила: `s3cmd getlifecycle` с теми же параметрами

### Как ставили правило в проекте

В проекте `s3cmd` не ставили: в `api` и в бэкапе уже был `minio-go`, у него для этих двух запросов есть методы `GetBucketLifecycle` и `SetBucketLifecycle`. Из них собрали одноразовую утилиту с двумя режимами, в репозиторий она не попала

**Шаг 1, `inspect`: что в бакете и какие правила уже стоят.**

```
верхний уровень бакета:
   before-update/
   regular/
объекты в regular/
  regular/  0 байт  2026-09-20 23:45
всего 1 объектов, 0 байт
lifecycle сейчас: Error response code NoSuchLifecycleConfiguration.
```

`NoSuchLifecycleConfiguration` это ответ «правил нет», ошибкой здесь он не является. В `regular/` тот самый маркер папки

**Шаг 2, `apply 60`: поставить правило и прочитать обратно.**

```go
cfg, err := c.GetBucketLifecycle(ctx, "mongo-backup") // текущие правила, если есть
if err != nil {
    cfg = lifecycle.NewConfiguration() // NoSuchLifecycleConfiguration: правил ещё нет
}
rule := lifecycle.Rule{
    ID:         "expire-regular-backups",
    Status:     "Enabled",
    RuleFilter: lifecycle.Filter{Prefix: "regular/"},
    Expiration: lifecycle.Expiration{Days: lifecycle.ExpirationDays(60)},
}
// остальные правила остаются в cfg и уходят обратно вместе с новым
cfg.Rules = append(cfg.Rules, rule)
err = c.SetBucketLifecycle(ctx, "mongo-backup", cfg)
```

```
установлено, читаю обратно:
lifecycle сейчас: 1 правил
  id="expire-regular-backups" status=Enabled prefix="regular/" days=60
```

| Что | Почему важно |
|---|---|
| сначала читать, потом ставить | `PUT ?lifecycle` заменяет всю конфигурацию бакета целиком. Правило, поставленное вслепую, стирает чужие |
| читать обратно после установки | ответ `200` на `PUT` говорит, что запрос принят. Прочитанное правило говорит, что хранилище его понимает |
| правила Vultr выполняет раз в сутки, в 00:00 UTC | объект старше 60 дней исчезает не мгновенно |
| на старой версии таблицы совместимости Vultr у lifecycle стояло `No`, на новой `Yes` | документации не хватило, поэтому поддержку подтвердили этой живой проверкой |

Само удаление ещё не наблюдалось: первые архивы станут старше 60 дней в декабре

## 4. Netdata: откуда брать цифры

Лимиты в compose стояли на глаз: `api` 200m, бот 250m, Netdata 600m. Netdata в стеке уже был и всё это время записывал память и CPU каждого контейнера. Оставалось достать данные

### Как достать

Netdata хранит метрики в своей базе на volume, это бинарные файлы, и прочитать их умеет только он сам. Зато у него есть REST API. Снаружи панель закрыта паролем Caddy, поэтому запросы идут изнутри контейнера:

```bash
ssh root@<IP> 'docker exec ec-netdata curl -s "http://localhost:8443/api/v1/info"'
```

Порт 8443 задан в `netdata.conf` проекта, по умолчанию Netdata слушает 19999

| Запрос | Что даёт |
|---|---|
| `/api/v1/info` | паспорт машины: 1 vCPU, 1955 МиБ RAM, версия Netdata |
| `/api/v1/charts` | список всех графиков (их 1407) и глубина хранения. Здесь видно, что данных за 6 суток с шагом 5 с |
| `/api/v1/data?chart=...` | сами значения одного графика |

```bash
docker exec ec-netdata curl -s "http://localhost:8443/api/v1/data?chart=cgroup_ec-mongodb.mem_usage&after=-518400&before=0&points=1&group=max&format=json&options=jsonwrap"
```

| Параметр | Что значит |
|---|---|
| `chart=cgroup_ec-mongodb.mem_usage` | график памяти контейнера `ec-mongodb`. Графики контейнеров называются `cgroup_<имя контейнера>.*` |
| `after=-518400&before=0` | последние 518 400 секунд, 6 суток |
| `points=1` | всё окно в одну точку. `points=6` даёт по точке на сутки, `points=144` по часу |
| `group=max` | чем сворачивать окно: `max`, `average`, или `percentile` с `group_options=95` |

Ответ, лишнее убрано:

```json
"result": {
  "labels": ["time", "ram", "swap"],
  "data": [[1791072000, 390.2891, 0]]
}
```

Пик памяти монги за 6 суток 390 МиБ. Дальше один ssh-сеанс прогнал 240 таких запросов: по каждому контейнеру и метрике `max`, `average` и p95

### Какие метрики брать

| Метрика | Что показывает | Зачем |
|---|---|---|
| `cgroup_<c>.mem_usage` | память контейнера вместе с page cache | пик сравнивается с `mem_limit` |
| `cgroup_<c>.mem`, измерение `anon` | память самих процессов, без кэша | лимит должен покрывать её с запасом |
| `cgroup_<c>.mem`, измерение `file` | page cache, ядро вытесняет его само | из-за него лимит поднимать не нужно |
| `cgroup_<c>.cpu` | CPU в процентах одного ядра | среднее и пик |
| `cgroup_<c>.throttled` | доля периодов, когда контейнер упёрся в `cpus` | троттлинг из урока 4, только за 6 суток |
| `cgroup_<c>.mem_some_pressure` | доля времени, когда процессы ждали память | около нуля значит, лимит ничего не душит |
| `mem.oom_kill` | OOM-убийства на хосте | за окно ноль |

Разница между `usage` и `anon` здесь главная. У Caddy `usage` 48 МиБ, а процессам из них нужно 15, остальное кэш. Лимит по одному `usage` вышел бы завышенным

### Что оказалось в данных

Память в МиБ, CPU в процентах одного ядра, окно 6 суток:

| Контейнер | usage max / p95 | anon max | CPU avg / max | throttled avg |
|---|---|---|---|---|
| `api` | 60,5 / 31,5 | 27 | 0,03 / 1,2 | 0% |
| `telegram-bot` | 131,7 / 106,9 | 99,5 | 0,02 / 10,7 | 0,05% |

## 6. Кейс: healthcheck, который ел CPU

Почасовые точки (`points=144`) по CPU монги показали странное: пик в каждом часе суток 22-26% ядра, ночного провала нет. Пользователей 2-3 в сутки, а нагрузка ровная круглые сутки. Так выглядит то, что запускается по таймеру

Таймер нашёлся в compose: healthcheck раз в 30 секунд вызывал `mongosh --eval ping`. `mongosh` написан на Node, каждый запуск это новый Node-процесс внутри cgroup монги, со своим CPU и памятью. Отсюда же `anon` до 254 МиБ при среднем 94

Решение: проверять, что порт принимает соединения, и реже

```yaml
    # Проба TCP вместо mongosh (каждый запуск mongosh это Node-процесс в cgroup монги).
    # start_interval обязателен: без него первая проба идёт через interval, и
    # up --wait в деплое падает по таймауту раньше, чем монга станет healthy
    healthcheck:
      test: ["CMD", "bash", "-c", "exec 3<>/dev/tcp/127.0.0.1/27017"]
      interval: 5m
      timeout: 10s
      retries: 3
      start_period: 40s
      start_interval: 5s
```

| Что | Зачем |
|---|---|
| `bash` и `/dev/tcp` | открыть TCP-соединение умеет сам `bash`, новых процессов кроме него нет |
| `interval: 5m` | базе на 2-3 пользователя проверка раз в 30 секунд не нужна |
| `start_interval: 5s` | пока контейнер стартует, проба идёт часто. Без этого первая проба случилась бы через 5 минут, `api` и бэкап ждут `service_healthy`, а деплой упал бы на `--wait-timeout 180` |

Сама проба работает: иначе `up --wait` не дождался бы монги и деплой упал бы. А вот то, что CPU ела именно она, пока гипотеза. Проверяется она той же метрикой: `cgroup_ec-mongodb.cpu` за сутки после деплоя. Если среднее упало с 3,9% ядра ниже 1%, причина была в пробе. Если осталось около 3,9%, гипотеза неверна, и дальше смотреть на саму базу

Следующий шаг продукта это фронтенд. Вопрос «влезет ли он на ту же виртуалку» без мониторинга решается покупкой машины побольше. С данными за 6 суток ответ считается:

## 8. Деплой, который откатывается сам

### Граф

Было `lint` → `deploy`. Стало:

```
кнопка ──▶ lint ──▶ deploy ──▶ release    деплой успешен
                           └──▶ redeploy   деплой упал
```

`deploy-pipeline.yml` из общего репозитория пайплайнов:

```yaml
jobs:
  lint:
    uses: EnjoyConnection/pipelines/.github/workflows/lint-infra.yml@main

  deploy:
    needs: lint
    if: ${{ !cancelled() }}
    uses: EnjoyConnection/pipelines/.github/workflows/deploy-infra.yml@main
    secrets: inherit

  redeploy:
    needs: deploy
    if: always() && needs.deploy.result == 'failure'
    uses: EnjoyConnection/pipelines/.github/workflows/deploy-infra.yml@main
    with:
      latest_tag: true
    secrets: inherit

  release:
    needs: deploy
    if: always() && needs.deploy.result == 'success'
    permissions:
      contents: write
    uses: EnjoyConnection/pipelines/.github/workflows/release-tag.yml@main
    with:
      new_tag: ${{ inputs.new_tag }}
```

### Почему тег ставится после деплоя

В уроке 9 тег это решение выкатить: пушнул `v1.3.0`, пайплайн его выкатил. Здесь наоборот, тег ставится только на коммит, который успешно задеплоился. Тогда последний тег в репозитории всегда означает «последнее состояние, на котором прод точно работал», и редеплою не нужно ничего вычислять: он берёт последний тег

В `infra` много коммитов-бампов от пайплайнов сервисов, деплой запускается кнопкой, и тег до деплоя там ничего не значил бы. Отсюда и правило, записанное в `CLAUDE.md` репозитория: тег на коммит, который не прошёл деплой, ставить нельзя, откат поедет на него

### Условия джоб

| Условие | Почему так |
|---|---|
| `always() && needs.deploy.result == 'failure'` | без `always()` GitHub неявно добавляет `success()`, и `redeploy` пропускался бы ровно тогда, когда нужен |
| `needs.deploy.result`, а не `failure()` | `failure()` смотрит на всех предков, включая `lint`. Упавший линт запустил бы редеплой при успешном деплое |
| отмена прогона руками | `deploy.result` будет `cancelled`, обе джобы пропускаются. Отмена не падение |
| упал и `redeploy` | дальше ничего не запускается, цикла нет |
| прогон после редеплоя | остаётся красным. Упавший `deploy` видно, редеплой его не маскирует |

### Редеплой

Отдельного workflow нет. `redeploy` зовёт тот же `deploy-infra.yml` с `latest_tag: true`, и шаги ssh и `ansible-playbook` не дублируются. В `deploy-infra.yml` добавлено:

```yaml
      - uses: actions/checkout@v5
        with:
          fetch-depth: 0

      - name: checkout latest tag
        if: inputs.latest_tag
        run: git checkout "$(git tag --sort=-v:refname | head -n1)"
```

| Что | Зачем |
|---|---|
| `fetch-depth: 0` | по умолчанию `checkout` тянет один коммит без тегов, и `git tag` вернул бы пустоту |
| `--sort=-v:refname` | сортировка по версии: `v0.10.0` выше `v0.9.0`. Обычная сортировка строк поставила бы наоборот |
| тег читает сама джоба | в этом прогоне новый тег до падения не появляется, гонки нет |

Откат идёт целиком: в compose из тега свои версии образов `api` и бота, свои лимиты и свой плейбук. Данные не откатываются, как и в уроке 7, рядом лежит дамп из `before-update/`

### Выпуск тега

`release-tag.yml`:

```yaml
jobs:
  release:
    runs-on: ubuntu-latest
    permissions:
      contents: write
    steps:
      - uses: actions/checkout@v5
        with:
          fetch-depth: 0

      - name: push tag
        env:
          NEW_TAG: ${{ inputs.new_tag }}
          GH_TOKEN: ${{ github.token }}
        run: |
          if [ -z "$NEW_TAG" ]; then
            latest=$(git tag --sort=-v:refname | head -n1)
            IFS=. read -r major minor patch <<< "${latest#v}"
            NEW_TAG="v${major}.${minor}.$((patch + 1))"
          fi
          git tag "$NEW_TAG"
          git push origin "$NEW_TAG"
          gh release create "$NEW_TAG" --generate-notes
```

| Что | Зачем |
|---|---|
| `new_tag` пустой | берётся последний тег, растёт патч: `v0.4.0` → `v0.4.1` |
| значение через `env`, а не `${{ }}` в теле скрипта | строка из поля ручного запуска не попадает в shell как код. В уроке 9 об этом же шла речь про `sed` |
| `permissions: contents: write` в трёх местах | в обёртке `infra`, в джобе `release` и в самом `release-tag.yml`. Права вложенного workflow ограничены правами вызывающего, одной верхней строки мало |
| `gh release create --generate-notes` | пуш тега создаёт только тег. Release с описанием из коммитов с прошлого тега создаётся отдельно |

Обёртка в `infra` после этого:

```yaml
name: pipeline
on:
  workflow_dispatch:
    inputs:
      new_tag:
        required: false

jobs:
  pipeline:
    permissions:
      contents: write
    uses: EnjoyConnection/pipelines/.github/workflows/deploy-pipeline.yml@main
    with:
      new_tag: ${{ inputs.new_tag }}
    secrets: inherit
```

Порядок выкладки: сначала `pipelines`, потом `infra`. Обёртка ссылается на `pipelines@main`, и новый input `new_tag` должен там уже быть

### Где редеплой не поможет

| Ситуация | Что будет |
|---|---|
| нет секрета, не пускает ssh-ключ, VM недоступна | плейбук из прошлого тега упадёт на том же месте. Редеплой лечит только случай, когда сломал сам коммит |
| падение посреди роли `deploy` | каталог деплоя уже стёрт, стек раскатывается из тега заново поверх тех же volume с данными |
| в репозитории нет ни одного тега и `new_tag` пустой | `release` упадёт на пустом значении |
| `new_tag` совпал с существующим тегом | `git tag` упадёт, ошибка видна в логе |

## 10. Грабли

| Что случилось | Причина | Как решили |
|---|---|---|
| на сервере `set: +: invalid option` | скрипт записан из Python на Windows, в конце строк `\r` | явный `newline="\n"` при записи файла, в репозитории концы строк держит `.gitattributes` |
| `source .env` ломает расписание | строка `BACKUP_CRON=*/2 * * * *` раскрывается оболочкой, `*` превращается в список файлов | значения читались через `grep` и `cut`, без `source` |
| правки кода бэкапа не доехали | `build:` без `--build` не пересобирает уже существующий образ | `up -d --build` в роли деплоя |

## 11. Практика: прод, который не страшно потерять

**Легенда.** Твой проект крутится на виртуалке, дамп снимается только перед деплоем. Ментор дал доступ к S3. Нужно, чтобы при смерти сервера терялось не больше суток данных, лимиты стояли по цифрам, а упавший деплой не оставлял прод лежать

### Что сделать

**1. Бэкап из урока 6 в проекте.** В уроке 6 ты собрал контейнер, который раз в сутки кладёт дамп в S3, на учебном проекте. Перенеси его в свой проект и пройди по таблице решений из раздела 2: что будет с оборванным дампом, что будет при сбое, сколько памяти ему нужно, как он узнаёт время запуска. Где твой бэкап решает иначе, чем бэкап монги, объясни почему

**2. Восстановление.** Подними пустую базу, восстанови последний бэкап из S3, покажи, что число строк совпало с продом

**3. Сбой.** Сломай бэкап нарочно, например неверным ключом S3. Покажи, что битый файл в бакет не попал и что следующая попытка случится сама

**4. Ротация.** Lifecycle-правило на своём префиксе. Перед установкой прочитай текущие правила бакета, после установки прочитай обратно. Покажи список объектов в своём префиксе за несколько суток

**5. Лимиты по данным.** Добавь Netdata в compose, дай ему поработать пару суток. Сними через API пики `mem_usage`, `anon` и `throttled` по своим контейнерам, посчитай лимиты по правилу из раздела 5 и проставь. Посмотри на CPU контейнера с базой по часам: если там ровные пики без ночного провала, найди, что запускается по таймеру

**6. Редеплой и тег.** При падении деплоя сам запускается редеплой с последней удачной версии, при успехе ставится тег. В твоей схеме из урока 9 тег ставится до деплоя, поэтому «последний тег» не значит «последний удачный деплой». Реши, откуда редеплой возьмёт версию, и объясни почему. Сломай деплой нарочно и покажи, что прод поднялся на прошлой версии

Результат: список объектов в S3 за несколько суток, вывод восстановления, лог упавшего бэкапа, правила lifecycle до и после, таблица лимитов было/стало с цифрами из Netdata, ссылки на прогоны в Actions (успешный с тегом, упавший с редеплоем)
