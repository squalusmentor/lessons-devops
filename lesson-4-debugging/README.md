# Урок 4. Базовая отладка приложений

Сайт из уроков 2 и 3 уже крутится в контейнере, локально или на виртуалке. Рано или поздно он начнёт тормозить, упадёт или перестанет отвечать. В этом уроке смотрим на сервер изнутри: сколько занято памяти и процессора, сколько места съел Docker, что происходит при нехватке ресурсов, доходят ли пакеты до сервера и где читать логи

Все команды ниже выполняются на виртуалке из урока 3, или локально, если под рукой нет сервера: заходишь по ssh и смотришь

## 1. Память, CPU, диск

Три первых вопроса, когда сервис тормозит: хватает ли памяти, свободен ли процессор, есть ли место на диске

**Память**: `free -h`

```
$ free -h
              total        used        free      shared  buff/cache   available
Mem:           7.8Gi       647Mi       6.5Gi       3.5Mi       792Mi       7.1Gi
Swap:          2.0Gi          0B       2.0Gi
```

| Столбец | Что значит |
|---|---|
| `total` | сколько памяти всего |
| `used` | занято процессами |
| `free` | ничем не занято |
| `buff/cache` | занято под кэш файловой системы, ядро отдаёт эту память первой при нехватке |
| `available` | сколько реально можно выделить новым процессам с учётом кэша |

Ориентируйся на `available`: низкий `free` при большом `available` это нормально, ядро использует свободную память под кэш и отдаёт её по первому запросу

**Диск**: `df -h`

```
$ df -h /
Filesystem      Size  Used Avail Use% Mounted on
/dev/sdd         63G  5.2G   55G   9%  /
```

Диск, забитый на 100%, роняет не только сайт: не может писать логи, не может создать временный файл, у баз данных начинаются ошибки записи

**CPU и память конкретного контейнера**: `docker stats`

```
$ docker stats --no-stream
CONTAINER ID   NAME                           CPU %     MEM USAGE / LIMIT     MEM %     NET I/O         BLOCK I/O       PIDS
43bdc585be8f   lesson-3-server-deploy-web-1   0.00%     8.082MiB / 7.756GiB   0.10%     4.06kB / 126B   9.27MB / 0B     7
```

Без `--no-stream` таблица обновляется в реальном времени, как `top`, только показывает контейнеры вместо процессов хоста

## 2. Сколько весит Docker и как чистить

После нескольких пересборок (`docker compose up -d --build` из урока 3) на диске остаются старые слои образов и кэш сборки, сколько именно, показывает `docker system df`:

```
$ docker system df
TYPE            TOTAL     ACTIVE    SIZE      RECLAIMABLE
Images          4         1         1.384GB   10.7MB (0%)
Containers      1         1         2.056MB   0B (0%)
Local Volumes   4         2         424MB     210MB (49%)
Build Cache     38        0         683.1MB   652.3MB (95%)
```

`RECLAIMABLE` показывает, сколько освободится, если почистить. В примере выше это в основном кэш сборки: каждый `docker build` кладёт слои в кэш, чтобы следующая сборка была быстрее, а старые слои никто не убирает сам

Что можно почистить:

| Команда | Что удаляет |
|---|---|
| `docker image prune` | висящие образы без тега (`<none>:<none>`) — остаются после пересборки с тем же именем |
| `docker system prune` | то же плюс остановленные контейнеры, неиспользуемые сети и весь кэш сборки |
| `docker system prune -a` | то же плюс **любой** образ, на который не ссылается ни один контейнер, даже если у него есть тег |

`-a`, самый радикальный вариант: если образ сайта сейчас не запущен (только собран), он попадёт под чистку, и следующий `docker compose up` будет собирать всё заново. Перед `prune -a` стоит сверить `docker ps -a`, особенно если на виртуалке крутится не только твой проект

На этом репозитории `docker system prune -f` реально освободил 652.3MB кэша сборки, накопленного за уроки 2 и 3, не тронув ни один рабочий контейнер

## 3. Load average, троттлинг и OOM

**Load average**: `uptime`

```
$ uptime
23:19:16 up 0 min,  1 user,  load average: 0.07, 0.02, 0.00
```

Одно ядро CPU выполняет в моменте ровно один процесс. Ядро Linux нарезает процессорное время на короткие кванты, тики, и по очереди раздаёт их всем процессам, которым нужен CPU: этим занимается планировщик (scheduler). Пока процессов меньше, чем ядер, каждый получает тики сразу, как попросил. Как только процессов, готовых выполняться, становится больше, чем свободных ядер, лишние встают в очередь и ждут своего кванта

Load average показывает среднюю длину этой очереди. Каждые несколько секунд ядро считает, сколько процессов сейчас либо уже выполняется на CPU, либо ждёт своей очереди (состояние R, runnable), либо ждёт ответа от диска (состояние D, uninterruptible sleep), и усредняет это число с затуханием за 1, 5 и 15 минут: отсюда три числа в выводе

Возьмём 0.07 из примера выше. Единственное ядро этой машины почти всё время было свободно: за последнюю минуту в среднем меньше одной десятой процесса претендовало на CPU в любой момент времени. Если бы один процесс грузил ядро на 100% всю минуту без перерыва, значение за эту минуту приблизилось бы к 1.00. Два таких процесса одновременно на одном ядре подняли бы load average к 2.00, оба процесса при этом остаются живы и работают, просто каждый получает вдвое меньше тиков в единицу времени

Сравнивать нужно с числом ядер (`nproc`): load average ниже `nproc` значит, ядрам хватает на всех, выше значит, кто-то стоит в очереди

Дальше разберём, что будет с сервисом при нехватке ресурсов: разница между нехваткой CPU и нехваткой памяти принципиальная

**Нехватка CPU: троттлинг.** Ограничиваем контейнер половиной ядра и запускаем бесконечный цикл:

```bash
docker run -d --name cputest --cpus="0.5" alpine sh -c "i=0; while true; do i=\$((i+1)); done"
```

```
$ docker stats --no-stream cputest
CONTAINER ID   NAME      CPU %     MEM USAGE / LIMIT   MEM %   PIDS
41a1675c9a8b   cputest   48.95%    940KiB / 7.756GiB    0.01%  1
```

Контейнер продолжает работать, просто получает меньше процессорного времени: CPU % упирается в лимит и дальше не растёт. Сервис продолжает отвечать на запросы, просто медленнее

**Нехватка памяти: OOM.** Ограничиваем контейнер 30 мегабайтами и пытаемся записать 200 мегабайт в память:

```bash
docker run -d --name oomtest -m 30m --memory-swap 30m alpine sh -c "dd if=/dev/zero of=/dev/shm/f bs=1M count=200"
```

```
$ docker ps -a --filter name=oomtest
CONTAINER ID   IMAGE     COMMAND   STATUS                     NAMES
e4665944829e   alpine    "dd ..."  Exited (137) 5 seconds ago  oomtest

$ docker inspect oomtest --format 'OOMKilled={{.State.OOMKilled}} ExitCode={{.State.ExitCode}}'
OOMKilled=true ExitCode=137
```

Ядро Linux следит за использованием памяти в cgroup контейнера, и, когда лимит превышен, убивает процесс намертво: `OOM killer`, сигнал `SIGKILL`, код выхода **137** (128 + номер сигнала 9). Никакого плавного торможения, секунду назад процесс работал, сейчас его нет

| | CPU в дефиците | Память в дефиците |
|---|---|---|
| Поведение | медленнее | процесс убит |
| Симптом | долгие ответы, растущий load average | контейнер `Exited (137)`, `OOMKilled=true` |
| Где смотреть | `docker stats`, `uptime` | `docker inspect`, `docker ps -a`, `dmesg \| grep -i oom` |

Не забудь убрать тестовые контейнеры: `docker rm -f cputest oomtest`

## 4. ping и traceroute

Если сайт не открывается, вопрос в том, где именно рвётся путь: сервер лежит, сеть до него не доходит или само приложение не отвечает

**ping**: жива ли машина

```
$ ping -c 4 8.8.8.8
PING 8.8.8.8 (8.8.8.8) 56(84) bytes of data.
64 bytes from 8.8.8.8: icmp_seq=1 ttl=62 time=1.76 ms
64 bytes from 8.8.8.8: icmp_seq=2 ttl=62 time=0.543 ms
64 bytes from 8.8.8.8: icmp_seq=3 ttl=62 time=0.548 ms
64 bytes from 8.8.8.8: icmp_seq=4 ttl=62 time=0.765 ms

--- 8.8.8.8 ping statistics ---
4 packets transmitted, 4 received, 0% packet loss, time 3059ms
```

Как в уроке 1: доходят пакеты, значит машина жива на сетевом уровне, про HTTP и приложение это ничего не говорит

**traceroute**: по какому пути идут пакеты и на каком хопе всё останавливается

```bash
traceroute 8.8.8.8      # Linux, если не установлен: sudo apt install traceroute
tracepath 8.8.8.8        # аналог без sudo, часто уже стоит
tracert 8.8.8.8           # то же самое в Windows
```

Каждая строка вывода соответствует одному узлу (хопу) на пути пакета. `* * *` вместо времени значит, что узел не ответил на пробный пакет, и это не всегда обрыв связи: многие роутеры сами глушат такие пакеты. Обрыв это когда одинаковый `* * *` идёт до самого конца и дальше цели не видно ни одного хопа. Полезно, когда пинг до сервера не проходит: traceroute показывает, докуда пакет вообще дошёл, до твоего провайдера, до хостера или потерялся где-то посередине

## 5. Логи в Linux

Логи контейнера смотрим уже знакомой командой из урока 2:

```bash
docker compose logs --tail 10 web
```

nginx в официальном образе не пишет в файлы: `access.log` и `error.log` это симлинки на `/dev/stdout` и `/dev/stderr`

```
$ docker exec lesson-3-server-deploy-web-1 ls -la /var/log/nginx
lrwxrwxrwx  1 root root  11 access.log -> /dev/stdout
lrwxrwxrwx  1 root root  11 error.log -> /dev/stderr
```

Поэтому `docker compose logs` это одновременно и лог контейнера, и лог nginx, отдельно за файлом на диске идти не нужно:

```
$ docker compose logs --tail 10 web
web-1  | 172.18.0.1 - - [16/Aug/2026:20:16:59 +0000] "GET / HTTP/1.1" 200 3987 "-" "curl/8.21.0" "-"
web-1  | 172.18.0.1 - - [16/Aug/2026:20:16:59 +0000] "GET /about/ HTTP/1.1" 200 4529 "-" "curl/8.21.0" "-"
web-1  | 172.18.0.1 - - [16/Aug/2026:20:16:59 +0000] "GET /no-such-page/ HTTP/1.1" 404 2405 "-" "curl/8.21.0" "-"
```

Логи самой виртуалки на уровень выше, это уже про систему целиком:

| Где | Что там |
|---|---|
| `journalctl` | системный журнал (systemd), все сервисы и ядро в одном месте |
| `/var/log/syslog` (Debian/Ubuntu) или `/var/log/messages` (RHEL/CentOS) | тот же журнал, но плоским текстовым файлом |
| `/var/log/auth.log` | попытки входа по ssh, полезно, если сервер ломится кто-то чужой |

```bash
journalctl -n 10              # последние 10 строк системного журнала
journalctl -k | grep -i oom   # искать OOM-килы среди сообщений ядра
tail -n 10 /var/log/syslog    # то же самое, но из плоского файла
```

Пример реального вывода `journalctl -n 5`:

```
Aug 16 23:17:00 host kernel: br-872e84dfafc2: port 1(vetha264aa3) entered disabled state
Aug 16 23:17:00 host systemd[1]: run-docker-netns-5a493c0aaa76.mount: Deactivated successfully.
Aug 16 23:17:00 host systemd-networkd[91]: br-872e84dfafc2: Link DOWN
```

Формат один и тот же везде: дата, хост, источник сообщения, само сообщение

## 6. Практика

На своей виртуалке из урока 3, по пунктам:

1. Посмотри `free -h`, `df -h` и `docker stats --no-stream`: сколько занято сейчас
2. Прогони `docker system df`, посчитай `RECLAIMABLE`, почисти через `docker system prune`, сравни цифры до и после
3. Посмотри `uptime` и `nproc`, сравни load average с числом ядер
4. Пропингуй и затрассируй свою виртуалку с локальной машины, а заодно какой-нибудь внешний сервис вроде 8.8.8.8, сравни путь и время отклика
5. Посмотри логи своего сайта через `docker compose logs --tail 10`, а также системный журнал виртуалки через `journalctl -n 10`
