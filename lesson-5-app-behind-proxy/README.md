# Урок 5. Приложение за прокси

До этого урока nginx отдавал файлы с диска: положили html, забрали html. Теперь за ним появляется приложение на Python, которое эти ответы генерирует само, и nginx превращается в reverse proxy: принимает запрос снаружи и передаёт его внутрь, приложению

В уроке два контейнера, которые разговаривают между собой по docker-сети, заголовки `X-Forwarded-*`, настройки через переменные окружения и логи приложения в stdout

---

## 1. Reverse proxy

Приложение и само умеет слушать порт, отдельный веб-сервер перед ним не обязателен. Так почти никто не делает, и вот почему:

- **Наружу открыт один порт.** Приложение слушает только внутри docker-сети, снаружи в него не попасть напрямую
- **HTTPS, редиректы, статика, лимиты живут в одном месте.** Сертификат из урока 3 лежит в nginx, приложение про TLS ничего не знает и знать не должно
- **Приложений может быть несколько.** Один nginx разводит запросы по путям и доменам между разными сервисами, каждый из которых занят только своим делом

Схема запроса:

```
браузер  ->  nginx (порт 8080 на твоей машине)  ->  приложение (порт 5000 внутри docker-сети)
```

## 2. Приложение

В [backend/](backend/) лежит приёмник событий из [project-list.md](../project-list.md): любой сервис присылает событие, потом это можно посмотреть

| Метод и путь | Что делает |
|---|---|
| `GET /health` | жив ли сервис, сколько событий в памяти |
| `POST /events` | записать событие, в теле `source` и `message` |
| `GET /events?source=` | список событий, свежие сверху, фильтр необязательный |
| `GET /whoami` | что приложение видит о запросе: адрес соединения и заголовки от прокси |
| `GET /apidocs` | Swagger UI |

### Раскладка по файлам

```
backend/
├── Dockerfile
├── main.py                собирает приложение и подключает роутеры
├── requirements.txt
└── source/
    ├── config.py          настройки из переменных окружения
    ├── logger.py          настройка логов в stdout
    ├── storage.py         где лежат события
    ├── routers/           какие есть URL
    │   ├── events.py
    │   └── system.py
    ├── handlers/          что происходит по этим URL
    │   ├── events.py
    │   └── system.py
    └── schemas/           что должно приехать в запросе
        └── event.py
```

Кода тут на страницу, и его можно было бы уместить в один файл. Разложен он так потому, что ровно так выглядит нормальный бэкенд, и дальше по курсу ты будешь смотреть на чужие проекты с такой же раскладкой

Путь одного запроса `POST /events` по файлам:

| Шаг | Файл | Что делает |
|---|---|---|
| 1 | [main.py](backend/main.py) | подключает блюпринт `events` с префиксом `/events` |
| 2 | [routers/events.py](backend/source/routers/events.py) | ловит метод и URL, достаёт тело запроса, отдаёт код ответа. Здесь же докстринг с описанием для Swagger |
| 3 | [schemas/event.py](backend/source/schemas/event.py) | проверяет, что в теле есть `source` и `message` |
| 4 | [handlers/events.py](backend/source/handlers/events.py) | собирает событие, берёт адрес клиента из заголовка, пишет строку в лог |
| 5 | [storage.py](backend/source/storage.py) | кладёт событие в хранилище |

Блюпринт (`Blueprint`) во Flask это группа маршрутов, которую `main.py` подключает одной строкой с общим префиксом. В FastAPI то же самое называется роутером

Хранилище пока живёт в памяти процесса: `deque` с ограничением по длине, перезапустил контейнер и событий нет. В уроке 6 на это место встанет Postgres, и переписывать придётся только `storage.py`, роутеры и хендлеры останутся как есть. Это и есть смысл раскладки по слоям

### Swagger

Страница, на которой видны все эндпоинты с описанием параметров, и каждый можно выполнить кнопкой вместо ручного curl. Подключается двумя вещами: `Swagger(app)` в `main.py` и YAML-описание в докстринге каждой ручки. По этим докстрингам библиотека собирает спецификацию `/apispec_1.json`, а страница `/apidocs` рисуется уже по ней

### Чем запускается

Приложение запускает gunicorn. Встроенный сервер Flask сюда не годится по той же причине, что `hugo server` в уроке 2: он написан для разработки и сам предупреждает об этом при старте. Строчка запуска в [backend/Dockerfile](backend/Dockerfile):

```dockerfile
CMD ["gunicorn", "--bind", "0.0.0.0:5000", "--access-logfile", "-", "main:app"]
```

| Аргумент | Что значит |
|---|---|
| `--bind 0.0.0.0:5000` | слушать на всех интерфейсах внутри контейнера. С `127.0.0.1` в контейнер не достучится даже nginx |
| `--access-logfile -` | писать лог запросов в stdout, дефис это и есть stdout |
| `main:app` | файл `main.py`, объект `app` внутри него |

## 3. Два контейнера

[docker-compose.yml](docker-compose.yml) целиком:

```yaml
services:
  backend:
    build: ./backend
    restart: unless-stopped
    environment:
      EVENT_LIMIT: ${EVENT_LIMIT:-100}
      LOG_LEVEL: ${LOG_LEVEL:-INFO}

  nginx:
    image: nginx:1.27-alpine
    restart: unless-stopped
    ports:
      - "${HTTP_PORT:-8080}:80"
    volumes:
      - ./nginx/site.conf:/etc/nginx/conf.d/default.conf:ro
    depends_on:
      - backend
```

Что здесь нового по сравнению с уроком 3:

| Ключ | Что значит |
|---|---|
| `build: ./backend` | контекст сборки это папка `backend`, Dockerfile берётся оттуда же. Отдельно указывать `dockerfile` не нужно |
| `image: nginx:1.27-alpine` | готовый образ с Docker Hub, без сборки. Свой Dockerfile для nginx здесь не нужен, конфиг заезжает внутрь монтированием |
| `volumes` | пробрасывает файл с хоста внутрь контейнера. Слева путь на диске, справа путь внутри, `ro` значит только на чтение |
| `depends_on` | порядок запуска: сначала `backend`, потом `nginx` |
| `ports` только у nginx | у `backend` его нет, поэтому снаружи приложение недоступно |

**Как контейнеры находят друг друга.** Compose поднимает для проекта общую сеть, и имена сервисов в ней работают как доменные имена. Поэтому в конфиге nginx написано `http://backend:5000`, где `backend` это имя сервиса из compose, а 5000 это порт внутри контейнера

Проверить прямо изнутри контейнера nginx (`wget` есть в alpine из коробки):

```
$ docker compose exec nginx wget -qO- http://backend:5000/health
{"limit":100,"status":"ok","stored":0}
```

А снаружи того же приложения нет:

```
$ curl http://localhost:5000/health
curl: (7) Failed to connect to localhost:5000 after 0 ms: Could not connect to server
```

**Про `depends_on`.** Имя `backend` в `proxy_pass` nginx резолвит один раз при старте. Если контейнера приложения в этот момент нет, nginx не запустится вообще, про это пункт 8

## 4. proxy_pass и заголовки X-Forwarded

[nginx/site.conf](nginx/site.conf) целиком:

```nginx
server {
    listen 80;
    server_name _;

    location / {
        proxy_pass http://backend:5000;

        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

`proxy_pass` заменяет собой `root` и `try_files` из уроков 2 и 3: вместо поиска файла на диске nginx открывает соединение с приложением и передаёт ответ обратно клиенту

Дальше начинается главная тонкость всей темы. Соединение с приложением открывает nginx, поэтому приложение по умолчанию видит его, а не клиента. Вот `/whoami` с закомментированными `proxy_set_header`:

```
$ curl -s http://localhost:8080/whoami
{"host":"backend:5000","remote_addr":"172.19.0.3","x_forwarded_for":null,"x_forwarded_proto":null,"x_real_ip":null}
```

`remote_addr` это адрес контейнера nginx, `Host` подменён на адрес апстрима, про клиента не известно ничего. Приложение в такой ситуации напишет в базу адрес прокси и сгенерирует ссылку на `backend:5000`, которая снаружи не открывается

С четырьмя строчками `proxy_set_header` картина другая:

```
$ curl -s http://localhost:8080/whoami
{"host":"localhost","remote_addr":"172.19.0.3","x_forwarded_for":"172.19.0.1","x_forwarded_proto":"http","x_real_ip":"172.19.0.1"}
```

| Заголовок | Что передаёт | Зачем приложению |
|---|---|---|
| `Host` | `$host`, домен из запроса клиента | генерировать ссылки и редиректы на правильный адрес |
| `X-Real-IP` | `$remote_addr`, адрес того, кто пришёл к nginx | писать в логи и в базу адрес клиента |
| `X-Forwarded-For` | `$proxy_add_x_forwarded_for`, цепочка адресов | то же самое, когда прокси несколько: каждый дописывает себя через запятую |
| `X-Forwarded-Proto` | `$scheme`, `http` или `https` | понимать, что клиент пришёл по HTTPS, хотя до приложения запрос доехал по HTTP |

`remote_addr` в приложении остался прежним, и так и должно быть: это по-прежнему адрес того, кто открыл соединение. Реальный адрес клиента приложение берёт из заголовка, этим занимается функция `client_ip()` в [handlers/events.py](backend/source/handlers/events.py)

Заголовки самые обычные, никакой магии в них нет: прислать `X-Real-IP` может кто угодно снаружи. Верить им можно ровно настолько, насколько ты уверен, что запрос пришёл через твой прокси

## 5. Переменные окружения

Настройки не зашиты в код и не лежат в compose, они приезжают снаружи. Один и тот же образ так работает и локально, и на сервере, меняется только `.env`

Копируешь шаблон [.env.example](.env.example) и правишь под себя:

```bash
cp .env.example .env
```

```
HTTP_PORT=8080
EVENT_LIMIT=100
LOG_LEVEL=INFO
```

Дальше эти три переменные расходятся по двум разным адресатам:

| Переменная | Кто читает | Как |
|---|---|---|
| `HTTP_PORT` | сам compose | подставляет в `ports` при запуске, внутрь контейнера не попадает |
| `EVENT_LIMIT`, `LOG_LEVEL` | приложение | compose кладёт их в окружение контейнера через `environment`, питон читает их через `os.environ.get` в [config.py](backend/source/config.py) |

Запись `${EVENT_LIMIT:-100}` означает «взять переменную, а если её нет, подставить 100». Поэтому проект запустится и без `.env`, на значениях по умолчанию

Что реально доехало внутрь контейнера:

```
$ docker compose exec backend env | grep -E 'EVENT_LIMIT|LOG_LEVEL'
EVENT_LIMIT=100
LOG_LEVEL=INFO
```

**Грабли.** Переменные попадают в контейнер один раз, в момент его создания. Поменял `.env`, сделал `docker compose restart`, ничего не изменилось:

```
$ docker compose restart backend && curl -s http://localhost:8080/health
{"limit":100,"status":"ok","stored":0}

$ docker compose up -d && curl -s http://localhost:8080/health
{"limit":3,"status":"ok","stored":0}
```

`restart` перезапускает процесс в старом контейнере, `up -d` замечает, что параметры изменились, и пересоздаёт контейнер заново

## 6. Логи в stdout

Приложение в контейнере не пишет логи в файл. Файл внутри контейнера умрёт вместе с контейнером, и по дороге его никто не прочитает. Вместо этого всё уходит в stdout, docker забирает этот поток, а `docker compose logs` его показывает. Ровно то же самое делает nginx из урока 4, где `access.log` это симлинк на `/dev/stdout`

В приложении за это отвечает [logger.py](backend/source/logger.py), который `main.py` вызывает до создания приложения:

```python
logging.basicConfig(
    stream=sys.stdout,
    level=settings.LOG_LEVEL,
    format="%(asctime)s %(levelname)s %(name)s %(message)s",
)
```

И `ENV PYTHONUNBUFFERED=1` в [backend/Dockerfile](backend/Dockerfile). Без него питон копит вывод в буфере и отдаёт пачками, а в `docker compose logs` в это время пусто, хотя запросы идут. Первая мысль в такой ситуации всегда «логи не работают», на самом деле они просто ещё не вылетели из буфера

В логе приложения два источника сразу: строки gunicorn про каждый запрос и наши собственные строки из `log.info`

```
$ docker compose logs --tail 3 backend
backend-1  | 2026-09-03 19:37:44,438 INFO source.handlers.events событие от deploy (172.19.0.1): release v1.2
backend-1  | 172.19.0.3 - - [03/Sep/2026:19:37:44 +0000] "POST /events HTTP/1.0" 201 105 "-" "curl/8.21.0"
backend-1  | 172.19.0.3 - - [03/Sep/2026:19:37:44 +0000] "GET /events?source=deploy HTTP/1.0" 200 128 "-" "curl/8.21.0"
```

`source.handlers.events` в строке `INFO` это имя модуля, который её написал: в каждом файле стоит `log = logging.getLogger(__name__)`, и по логу сразу видно, чей это вывод

Тот же самый запрос в логе nginx:

```
$ docker compose logs --tail 1 nginx
nginx-1  | 172.19.0.1 - - [03/Sep/2026:19:37:44 +0000] "GET /events?source=deploy HTTP/1.1" 200 128 "-" "curl/8.21.0" "-"
```

Сравни адреса в начале строк. У nginx это `172.19.0.1`, адрес клиента, у приложения `172.19.0.3`, адрес самого nginx. Про клиента приложение знает только то, что ему передали заголовком, и в строке `INFO` виден именно он

`LOG_LEVEL` управляет тем, что попадёт в вывод. На `INFO` строки уровня `DEBUG` отбрасываются, на `DEBUG` появляются:

```
$ docker compose logs --tail 2 backend
backend-1  | 2026-09-03 19:45:58,334 DEBUG source.handlers.events отдали 0 событий, фильтр source=None
backend-1  | 172.19.0.3 - - [03/Sep/2026:19:45:58 +0000] "GET /events HTTP/1.0" 200 24 "-" "curl/8.21.0"
```

## 8. Что видно, когда сломалось

Три ошибки, на которые натыкаются при первой настройке прокси. Все три ловятся в `docker compose logs nginx`

| Что отдаёт nginx | Строка в логе nginx | Причина |
|---|---|---|
| `502 Bad Gateway` | `connect() failed (111: Connection refused) while connecting to upstream` | приложение живо, но слушает другой порт, не тот, что написан в `proxy_pass` |
| `502` или `504 Gateway Time-out` | `connect() failed (113: Host is unreachable)` либо `upstream timed out (110: Operation timed out)` | контейнер приложения остановлен, до него не доходят пакеты |
| ничего, nginx падает при старте | `[emerg] host not found in upstream "backend"` | имя из `proxy_pass` не резолвится: опечатка в имени сервиса либо контейнер приложения ни разу не поднимался |

Первый случай самый частый и самый понятный: соединение отвергнуто сразу, значит приложение отвечает, просто не там, где его ждут

Во втором случае код ответа зависит от того, успела ли исчезнуть сеть остановленного контейнера. Отвергнутое соединение даёт 502 сразу, ушедшие в никуда пакеты дают 504 через минуту ожидания. Причина одна и та же

Третий случай выглядит непривычно: из-за `restart: unless-stopped` контейнер nginx не остаётся мёртвым, он перезапускается по кругу. В `docker compose ps` при этом мелькает то `Restarting`, то `Up 2 seconds`, и понять что-то можно только по логу:

```
$ docker compose logs nginx | grep emerg | tail -1
nginx-1  | nginx: [emerg] host not found in upstream "bakcend" in /etc/nginx/conf.d/default.conf:6
```

Проверить последнее звено всегда можно изнутри nginx, минуя прокси целиком:

```bash
docker compose exec nginx wget -qO- http://backend:5000/health
```

Отвечает, значит приложение и сеть в порядке, проблема в конфиге. Не отвечает, значит идти в `docker compose logs backend`

## 9. Практика: выкатить бэкенд за прокси

**Легенда.** Тебе дали бэкенд и сказали выкатить его наружу. В код не лезешь, ты его не писал: смотришь, какой порт он слушает и какие переменные окружения читает, и заворачиваешь его за nginx

### Что сделать

**1. Взять приложение.** Любое, ограничений нет: попроси нейронку написать маленький сервис на Flask или FastAPI, возьми готовый пример с GitHub, напиши сам. Требования к нему:

- слушает порт и отдаёт JSON
- разложен по файлам, а не свален в один: маршруты, логика и работа с данными по разным местам
- две-три настройки читает из переменных окружения
- пишет логи в stdout
- есть Swagger, чтобы дёргать эндпоинты кнопками, а не курлами
- есть эндпоинт, который показывает, что приложение видит о запросе (свой `/whoami`)

**2. Собрать compose из двух сервисов**: приложение и nginx. Наружу торчит только nginx, у приложения `ports` нет вообще

**3. Написать конфиг nginx** с `proxy_pass` и заголовками, чтобы приложение видело настоящий адрес клиента и настоящий `Host`. Проверь через свой `/whoami`, что заголовки доехали

**4. Вынести настройки в `.env`.** В `docker-compose.yml` не должно остаться ни одного захардкоженного значения: ни порта наружу, ни настроек приложения

**5. Поймать все три ошибки из пункта 8 руками.** Поставь неправильный порт в `proxy_pass`, останови контейнер приложения, сделай опечатку в имени сервиса. Каждый раз смотри, что отдаёт nginx и что пишет в лог

**6. Показать логи на один запрос.** Дёрни любой эндпоинт и найди этот запрос в логах обоих контейнеров. Объясни, почему адреса в двух логах разные
