# Урок 9. Ansible в пайплайне

В уроке 7 деплой был SSH-командой из пайплайна, и сервер всё ещё жил как рабочая копия git: `git pull`, токен к репозиторию, `.env`, поправленный руками. В уроке 8 появился плейбук, который готовит сервер целиком, но запускается он с твоего ноутбука

Здесь они встречаются. Джоба деплоя вызывает плейбук, сервер больше не держит ни git, ни токен, а путь от `git push origin v1.3.0` до работающего сервиса проходит без единой ручной команды. Откат остаётся кнопкой, только теперь он возвращает и код, и конфиги той версии

---

## 1. Что меняется

| | Урок 7 | Этот урок |
|---|---|---|
| Кто выкатывает | `ssh` с командами из `deploy.yml` | `ansible-playbook` из `deploy.yml` |
| Откуда сервер берёт compose и конфиги | `git pull` на сервере | раннер привозит их сам |
| Что лежит на сервере | клон репозитория с токеном в `.git/config` | `docker-compose.yml`, `nginx/site.conf`, `.env` |
| Откуда `.env` | правится руками на сервере | собирается плейбуком из секретов GitHub |
| Что откатывает кнопка | образ, а compose остаётся из `main` | образ, compose, конфиги и сам плейбук той версии |
| Где адрес сервера | переменные `DEPLOY_HOST`, `DEPLOY_USER` | `inventory.ini` в репозитории |

Файлы урока: [deploy.yml](.github/workflows/deploy.yml) и [ansible/](ansible/). [pipeline.yml](../lesson-7-cicd/.github/workflows/pipeline.yml) остаётся из урока 7 без изменений: линт, сборка, вызов деплоя

## 2. Push вместо pull

В уроке 7 сервер сам ходил в git за свежим compose. Для этого на нём лежит токен к репозиторию, и сервер превращается в рабочую копию, которая может разъехаться с репозиторием: кто-то поправил файл прямо на сервере, и следующий `git pull` упал на конфликте

Направление можно развернуть. Раннер чекаутит репозиторий у себя и сам привозит на сервер ровно те файлы, которые нужны. Эта схема называется push, и ansible для неё и сделан

| | Pull (урок 7) | Push (этот урок) |
|---|---|---|
| Доступ к git с сервера | нужен, токен лежит на сервере | не нужен |
| Правка руками на сервере | конфликт на следующем `git pull` | перезаписывается следующим деплоем |
| Что нужно раннеру | SSH до сервера | SSH до сервера |
| Починить сервер, когда GitHub недоступен | `git pull` из другого места | прогнать тот же плейбук с ноутбука, урок 8 |

В живом проекте выбор сделали так же и записали с обоснованием: на сервере нет git-кредов и рабочей копии, откат это перезапуск пайплайна на старом коммите, руками на машине ничего не делается. Цену тоже записали: раннеру нужен приватный SSH-ключ в секретах GitHub

## 3. Джоба деплоя

[deploy.yml](.github/workflows/deploy.yml) целиком:

```yaml
jobs:
  deploy:
    runs-on: ubuntu-latest
    concurrency: deploy
    timeout-minutes: 15
    defaults:
      run:
        working-directory: ansible
    steps:
      - uses: actions/checkout@v5
        with:
          ref: ${{ inputs.tag }}

      - run: ansible-galaxy collection install -r requirements.yml

      - name: SSH-ключ и ключ сервера
        env:
          SSH_PRIVATE_KEY: ${{ secrets.SSH_PRIVATE_KEY }}
          SSH_KNOWN_HOSTS: ${{ vars.SSH_KNOWN_HOSTS }}
        run: |
          mkdir -p ~/.ssh
          echo "$SSH_KNOWN_HOSTS" >> ~/.ssh/known_hosts
          eval "$(ssh-agent -s)" > /dev/null
          echo "$SSH_PRIVATE_KEY" | ssh-add -
          echo "SSH_AUTH_SOCK=$SSH_AUTH_SOCK" >> "$GITHUB_ENV"

      - name: ansible-playbook ${{ inputs.tag }}
        env:
          POSTGRES_PASSWORD: ${{ secrets.POSTGRES_PASSWORD }}
          TAG: ${{ inputs.tag }}
        run: ansible-playbook site.yml -e "app_tag=$TAG"
```

| Что | Зачем |
|---|---|
| `working-directory: ansible` | все `run` выполняются из папки с `ansible.cfg`, иначе ansible не найдёт inventory |
| `checkout` с `ref: inputs.tag` | берётся код того же тега, что и образ. Плейбук, compose и конфиги той же версии |
| `ansible-galaxy collection install` | ставит `community.docker` для модуля compose. Сам ansible на раннере GitHub уже есть |
| шаг с SSH-ключом | тот же, что в уроке 7: ключ в `ssh-agent`, на диск не пишется |
| `env` у последнего шага | секрет попадает в окружение, плейбук читает его через `lookup('env', ...)`, как с ноутбука |

Шаг с ключом и строка `ansible-playbook site.yml` взяты из живого проекта. Сам ansible там тоже не ставится отдельно, берётся с раннера. Обратная сторона: версия ansible меняется вместе с образом раннера, без коммита в твой репозиторий. Если это станет проблемой, ansible ставится явно с прибитой версией через `pipx install`

`SSH_KNOWN_HOSTS` здесь нужен так же, как в уроке 7. В живом проекте вместо этого в `ansible.cfg` отключена проверка ключа сервера, `host_key_checking = False`: виртуалки там пересоздавались, и ключ каждый раз был новым. Цена такого решения: раннер пойдёт на любой сервер, который ответит по этому IP, и отдаст ему секреты из `.env`. Строка из `ssh-keyscan` в переменной закрывает это, а при пересоздании виртуалки её перезаписывают один раз

Переменные `DEPLOY_HOST` и `DEPLOY_USER` из урока 7 больше не нужны: адрес сервера и пользователь живут в [inventory.ini](ansible/inventory.ini), в репозитории

## 4. Путь секрета

Пароль от базы проходит путь из пяти звеньев, и на каждом его можно потерять:

| Звено | Где | Как передаётся |
|---|---|---|
| 1 | Settings → Secrets → `POSTGRES_PASSWORD` | хранится в GitHub |
| 2 | `env` шага в [deploy.yml](.github/workflows/deploy.yml) | переменная окружения процесса `ansible-playbook` |
| 3 | [group_vars/all.yml](ansible/group_vars/all.yml) | `lookup('env', 'POSTGRES_PASSWORD')`, проверка `assert` |
| 4 | [env.j2](ansible/roles/app/templates/env.j2) | файл `.env` на сервере с правами `0600` |
| 5 | [docker-compose.yml](docker-compose.yml) | `${POSTGRES_PASSWORD}` в окружении контейнеров |

Секретов в `deploy.yml` ровно столько, сколько нужно плейбуку, каждый назван явно. В живом проекте в окружение плейбука уходят все секреты репозитория разом:

```yaml
      - name: ansible-playbook
        env:
          SECRETS: ${{ toJSON(secrets) }}
        run: |
          eval "$(jq -r 'to_entries[] | "export \(.key)=\(.value | @sh)"' <<< "$SECRETS")"
          ansible-playbook site.yml
```

Удобно: новый секрет достаточно завести в GitHub, пайплайн трогать не нужно. Но вместе с нужными пятью в окружение ansible попадают и токен Docker Hub, и токен для пуша в другой репозиторий, и сам SSH-ключ. Любая задача плейбука видит их все. Явный список в `env` длиннее, зато по нему видно, что куда уходит, и лишнего плейбук не получает

## 5. Дамп перед деплоем

Пока деплой выкатывал человек, он мог перед релизом снять дамп, как в уроке 6. Кнопка сама этого не сделает, значит делает плейбук. В роль `app` добавлены две задачи перед запуском стека, [roles/app/tasks/main.yml](ansible/roles/app/tasks/main.yml):

```yaml
- name: Запущена ли уже база
  ansible.builtin.command: docker compose ps --status running --quiet postgres
  args:
    chdir: "{{ app_dir }}"
  register: db_running
  changed_when: false

- name: Дамп базы перед обновлением
  ansible.builtin.shell: >-
    docker compose exec -T postgres
    pg_dump -U {{ postgres_user }} --clean --if-exists {{ postgres_db }}
    > backups/before-{{ app_tag }}-{{ ansible_facts['date_time']['iso8601_basic_short'] }}.sql
  args:
    chdir: "{{ app_dir }}"
  when: db_running.stdout | length > 0
```

| Что | Зачем |
|---|---|
| `register: db_running` | кладёт весь ответ модуля в переменную. Из него дальше читается `stdout`, то, что команда напечатала |
| `changed_when: false` | `docker compose ps` только смотрит. Без этой строки ansible считал бы её изменением, как любой `command` |
| `when: db_running.stdout \| length > 0` | `--quiet` печатает id контейнера или ничего. На самом первом деплое базы ещё нет, дамп пропускается |
| `shell` вместо `command` | нужен `>`, перенаправление в файл. `command` запускает программу напрямую, без shell, и `>` для него просто символ |
| `ansible_facts['date_time']` | время с сервера, ansible собирает его сам при подключении. Имена файлов сортируются по времени как строки |

Главное свойство этих задач: если `pg_dump` вернул ошибку, плейбук останавливается, и до задачи с compose дело не доходит. Старая версия продолжает работать, новая не выкатывается, пока не починишь бэкап

Дамп это действие, у него нет состояния «уже сделано», поэтому задача будет `changed` на каждом прогоне. Второй прогон урока 8 давал `changed=0`, теперь честно даёт `changed=1`

В живом проекте тот же гейт, только для MongoDB и с заливкой в S3:

```yaml
- name: Stop everything except the database
  ansible.builtin.command:
    cmd: "docker compose stop {{ deploy_stop_first | join(' ') }}"
    chdir: "{{ deploy_dir }}"
  when: existing_compose.stat.exists

- name: Dump the database
  ansible.builtin.command:
    cmd: "docker exec {{ mongo_container }} mongodump --archive=/backup/{{ backup_file }} --gzip"
  when: mongo_ps.stdout | length > 0
```

Там перед дампом останавливаются все, кто пишет в базу, чтобы дамп был снят без конкурентной записи. Обратная сторона такого порядка: если дамп или заливка упали, бот и бэкенд уже остановлены, а до их запуска плейбук не дойдёт. Деплой не случился, но и прод лежит. Здесь дамп снимается на живом стеке, `pg_dump` это позволяет без остановки, как в уроке 6, и упавший дамп ничего не ломает

Что такое S3, как устроен бакет проекта и что в нём происходит, подробно разобрано в [уроке 10](../lesson-10-backup-limits-redeploy/#3-s3-стандарт-и-бакет-проекта)

Дампы копятся в `/opt/events/backups` на том же диске, что и база. От кривой миграции это спасает, от умершего диска нет. Как увезти их с сервера и чистить старые, урок 10

## 6. Одна кнопка и откат

Релиз:

```bash
git tag v1.3.0
git push origin v1.3.0
```

`lint` → `build` → `deploy`, и через пару минут `curl http://<IP>/health` отвечает `"version":"v1.3.0"`

Откат: **Actions → deploy → Run workflow**, `tag` старой версии. Из-за `ref: inputs.tag` в `checkout` раннер берёт код этого тега целиком. На сервер уезжают compose и конфиг nginx той версии, в `.env` пишется её образ, и выполняется тот плейбук, который был у неё. Сервер целиком возвращается в состояние, в котором был на этом релизе, вместе с образом

Одно ограничение: откатиться так можно только на тег, в котором уже есть папка `ansible/`. Теги из уроков 7 и раньше плейбука не содержат, и джоба упадёт на первом шаге. В живом проекте то же самое: на старые теги, сделанные до переезда на ansible, откатиться кнопкой нельзя

Как и в уроке 7, откат не трогает данные. Если новая версия успела поменять базу, рядом лежит дамп, снятый перед ней

### Как это устроено в живом проекте

Там сервисов два, у каждого свой репозиторий, и версии выкатываются независимо. Поэтому состояние сервера вынесено в отдельный репозиторий `infra`: `docker-compose.yml` с тегами всех образов и `ansible/`

```
репозиторий сервиса:   кнопка → линт → сборка → коммит "bump api to v0.3.10" в infra
репозиторий infra:     кнопка → ansible-playbook → сервер
```

Версия там живёт в compose, в git, через `-e` её никто не передаёт. Пайплайн сервиса после сборки сам правит строку `image:` и коммитит:

```yaml
      - name: bump tag
        run: |
          sed -i -E "s#(image:[[:space:]]*${{ inputs.image_name }}:)[^[:space:]\"']+#\1${{ inputs.new_tag }}#" ${{ inputs.compose_path }}

      - name: fail if nothing changed
        run: |
          if git diff --quiet -- ${{ inputs.compose_path }}; then
            echo "образ ${{ inputs.image_name }} не найден в ${{ inputs.compose_path }}, менять нечего"
            exit 1
          fi
```

Что это даёт: история `infra` и есть журнал деплоев, каждый бамп отдельным коммитом, а откат это `git revert` бампа и та же кнопка. Проверка после `sed` не даёт пайплайну молча ничего не поменять, если имя образа в compose разошлось с настройками

Что стоит сделать иначе, если повторять эту схему. Значения `inputs` вклеиваются прямо в текст команды через `${{ }}`, и кавычка или `#` в теге ломают `sed`. Надёжнее передавать их через `env`, как `TAG` в этом уроке. И два сервиса, собранные одновременно, будут пушить в `main` репозитория `infra` наперегонки, второй пуш отклонится. Лечится `concurrency` на джобе бампа

Деплой из `infra` там запускается только кнопкой, коммиты его не запускают. Ручное подтверждение через Environments с обязательным ревьюером GitHub даёт в приватных репозиториях только на тарифе Enterprise, поэтому роль подтверждения играет сама кнопка. Для одного проекта в одном репозитории всё это лишнее: тег сам по себе и есть решение выкатить

## 7. Что видно, когда сломалось

| Где упало | Что в логе | Причина |
|---|---|---|
| `checkout` | `A branch or tag with the name 'v1.0.0' could not be found` | такого тега нет в репозитории |
| `ansible-playbook` | `Assertion failed`, текст про `POSTGRES_PASSWORD` | не заведён секрет `POSTGRES_PASSWORD` или он не передан в `env` шага |
| `ansible-playbook` | `UNREACHABLE! ... Host key verification failed` | `SSH_KNOWN_HOSTS` пустая или сервер пересоздан с новым ключом |
| `ansible-playbook` | `UNREACHABLE! ... Permission denied (publickey)` | публичная часть CI-ключа не лежит у `ansible_user` из inventory |
| `ansible-playbook` | `the playbook: site.yml could not be found` | не выставлен `working-directory: ansible`, команда запущена из корня репозитория |
| задача дампа | `pg_dump: error: ...` | база не отвечает или неверный пользователь. Деплой остановлен до обновления, прод на старой версии |
| задача compose | контейнер `backend` `unhealthy` | новая версия не проходит `/health`. Откат кнопкой, потом `docker compose logs backend` на сервере |

## 8. Практика: деплой в одну кнопку

**Легенда.** Проект выкатывается плейбуком с ноутбука. Нужно, чтобы релиз был одним тегом, откат одной кнопкой, а на сервере не осталось ни git, ни токенов

### Что сделать

**1. Деплой через ansible.** `deploy.yml` из урока 7 вызывает плейбук из урока 8. SSH-ключ в `ssh-agent`, ключ сервера из переменной, пароль базы из секрета

**2. Один тег.** `git push origin v*` проходит линт, сборку и деплой без ручных шагов. `curl /health` показывает новую версию

**3. Гейт на дамп.** Перед обновлением снимается дамп базы. Сломай дамп нарочно (например, неверный пользователь в `pg_dump`) и покажи, что деплой остановился до обновления, а прод остался на прошлой версии

**4. Откат кнопкой.** Откати на прошлый тег и покажи, что вернулся не только образ: поменяй в новом релизе что-нибудь в `nginx/site.conf` и убедись, что после отката конфиг на сервере старый

**5. Чистый сервер.** Удали с сервера клон репозитория из урока 3 и отзови токен, которым он клонировался. Выкати новую версию и покажи, что деплою они не нужны

**6. Секреты.** Пройди по таблице из пункта 4 для своего проекта: где живёт каждый секрет, как он доезжает до контейнера, где его видно в логах пайплайна

Результат: ссылки на прогоны в Actions (релиз, упавший дамп, откат), вывод `curl /health` до и после отката, `ls -la /opt/<проект>` на сервере без `.git`
