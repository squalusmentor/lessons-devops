## 2. nginx

**Что это.** Веб-сервер: процесс, который слушает порт (80 для http, 443 для https),
принимает HTTP-запросы и отвечает на них. В нашем случае — отдаёт файлы с диска.

**Зачем он, если статику отдавал и `hugo server`.** Dev-сервер нужен, чтобы
разработчик видел свои правки. Он не рассчитан на нагрузку, не умеет в https и
живёт под присмотром. В прод ставят nginx.

**Где что лежит** (внутри контейнера, в обычном Linux то же самое):

```
/etc/nginx/nginx.conf        главный конфиг, в нём include /etc/nginx/conf.d/*.conf;
/etc/nginx/conf.d/*.conf     конфиги отдельных сайтов — сюда кладём свой
/usr/share/nginx/html        файлы сайта
/var/log/nginx/error.log     что сломалось — первое место, куда смотреть
```

**Наш конфиг** целиком — [nginx/site.conf](nginx/site.conf):

```nginx
server {
    listen 80;                        # какой порт слушать
    server_name localhost;            # для какого домена (берётся из заголовка Host)
    root /usr/share/nginx/html;       # где на диске лежат файлы
    index index.html;                 # что отдать, если запросили папку

    location / {
        try_files $uri $uri/ =404;    # файл -> папка -> 404
    }

    error_page 404 /404.html;         # своя страница вместо стандартной
}
```

Это полный рабочий конфиг статического сайта. Всё остальное (https, сжатие,
кэш, проксирование на приложение) — надстройки, до них дойдём, когда понадобятся.

Команды:

```bash
nginx -t            # проверить синтаксис, НЕ запуская. Делать всегда перед reload
nginx -s reload     # применить конфиг без разрыва соединений
```

## 3. Docker

**Что это.** Способ упаковать приложение вместе со всем, что ему нужно —
окружением, библиотеками, конфигами — в один архив (**образ**), который
запускается одинаково где угодно.

**Два слова, которые путают:**
- **Образ (image)** — слепок на диске, не работает. Как установочный ISO.
- **Контейнер (container)** — запущенный экземпляр образа, это процесс. Из одного
  образа можно поднять хоть двадцать контейнеров.

**А без докера можно?** Можно. Ставишь на сервер nginx, кладёшь файлы, правишь
конфиг — работает. Так почти никто не делает, и вот почему:

- **Линукс.** Прод — это Linux. Твоя машина — Windows. Без контейнера ты
  разрабатываешь в одном окружении, а выкатываешь в другое, и «у меня локально
  работало» становится образом жизни.
- **Зависимости.** Проекту нужен nginx 1.27 и Hugo 0.164, соседнему на том же
  сервере — версии постарше. В контейнерах у каждого своё, и они не дерутся.
- **Танцы с бубном.** Развернуть окружение руками = страница инструкций, которая
  устаревает через месяц и которую надо повторять на каждом новом сервере.
  Dockerfile — та же инструкция, только исполняемая и всегда актуальная.

Отсюда главный смысл: **окружение описано кодом и лежит в репозитории рядом с проектом**.

Базовые команды:

```bash
docker images                      # какие образы есть
docker ps                          # какие контейнеры работают
docker ps -a                       # включая остановленные
docker logs -f lesson2-web         # логи контейнера, -f следить в реальном времени
docker exec -it lesson2-web sh     # зайти внутрь работающего контейнера
docker stop / start / rm <имя>     # остановить / запустить / удалить
```

## 4. Dockerfile

[Dockerfile](Dockerfile) — рецепт образа. Каждая инструкция создаёт **слой**;
слои кэшируются, поэтому повторная сборка идёт за секунды.

У нас **два этапа** (multi-stage build):

```dockerfile
# 1. builder: ставим Hugo, собираем сайт из урока 1
FROM ghcr.io/gohugoio/hugo:v0.164.0 AS builder
WORKDIR /src
COPY lesson-1-base-web/ ./
RUN hugo --minify --baseURL "${HUGO_BASEURL}"

# 2. runtime: чистый nginx + только результат сборки
FROM nginx:1.27-alpine
RUN rm /etc/nginx/conf.d/default.conf
COPY lesson-2-nginx-docker/nginx/site.conf /etc/nginx/conf.d/site.conf
COPY --from=builder /src/public /usr/share/nginx/html
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]
```

Что здесь важно:

- **Два этапа.** В итоговый образ не попали ни Hugo, ни исходники — только nginx
  и готовые html. **48 МБ** вместо ~400 МБ.
- **Версии зафиксированы** (`v0.164.0`, `1.27-alpine`), а не `latest`. Иначе сборка,
  которая работала вчера, завтра развалится на новой версии.
- **`daemon off`** — nginx не должен уходить в фон. Контейнер живёт ровно столько,
  сколько живёт его главный процесс.
- **`EXPOSE 80`** ничего не пробрасывает, это документация. Пробрасывает `-p 8080:80`.
- **Контекст сборки — корень репозитория**, а не эта папка: `COPY` не умеет выходить
  за пределы контекста, а нам нужен `lesson-1-base-web/`. Поэтому пути в Dockerfile
  идут от корня, а в конце команды сборки стоит `..`.

## 5. Сборка и запуск

Обе команды — из папки `lesson-2-nginx-docker`.

### Сборка

```bash
docker build -f Dockerfile -t lesson2-web:latest ..
```

| Параметр | Что значит |
|---|---|
| `-f Dockerfile` | какой файл-рецепт брать |
| `-t lesson2-web:latest` | как назвать образ: `имя:тег`. Без `-t` образ будет безымянным |
| `..` | **контекст сборки** — папка, которую docker отправит себе. Здесь корень репозитория, потому что нужен `lesson-1-base-web/` |

### Запуск

```bash
docker run -d --name lesson2-web -p 8080:80 lesson2-web:latest
```

| Параметр | Что значит |
|---|---|
| `-d` | в фоне (detached). Без него терминал останется занят |
| `--name lesson2-web` | имя контейнера, чтобы обращаться к нему по имени, а не по хешу |
| `-p 8080:80` | **проброс порта: `порт_на_localhost` : `порт_внутри_контейнера`**. Внутри nginx слушает 80, снаружи заходим на 8080 |
| `lesson2-web:latest` | какой образ запускать (всегда последним аргументом) |

**Про `-p` подробнее.** Меняешь только **левое** число — `site.conf` трогать не надо:

```bash
docker run -d --name lesson2-web -p 9090:80 lesson2-web:latest   # сайт на localhost:9090
docker run -d --name lesson2-web -p 80:80   lesson2-web:latest   # просто localhost
```

Без `-p` контейнер запустится и будет работать, но снаружи в него не попасть.
Порт занят другим контейнером — docker откажется стартовать: `port is already allocated`.

**Пересобрать после правок** — контейнер надо удалить, новый образ он не подхватит сам:

```bash
docker rm -f lesson2-web
docker build -f Dockerfile -t lesson2-web:latest ..
docker run -d --name lesson2-web -p 8080:80 lesson2-web:latest
```

> `docker compose` умеет то же самое одной строкой и нужен, когда образов несколько
> (сайт + база + бэкенд). Это следующие уроки.

### Проверка

Сайт: **http://localhost:8080**

```bash
curl -I http://localhost:8080/                 # 200, Server: nginx
curl -I http://localhost:8080/about/           # 200
curl -I http://localhost:8080/no-such-page/    # 404, отдаётся наша страница
```

Заглянуть внутрь работающего контейнера:

```bash
docker exec -it lesson2-web sh
ls /usr/share/nginx/html          # вот они, собранные файлы сайта
cat /etc/nginx/conf.d/site.conf   # вот наш конфиг
nginx -t                          # проверить синтаксис
exit
```

## 7. Практическая работа: упаковать чужой сайт

**Легенда.** Тебе дали фронтенд и сказали «подними». Ровно так выглядит реальная
задача, когда пишешь CI/CD для фронта или разворачиваешь чужое приложение:
кода ты не писал, как он устроен — разбираешься на месте.

### Что сделать

**1. Взять сайт.** Любым способом, тут никаких ограничений:

- попросить нейронку сгенерировать лендинг;
- скачать бесплатный шаблон ([html5up.net](https://html5up.net), [startbootstrap.com](https://startbootstrap.com));
- взять готовый с GitHub;
- написать самому.

Единственное требование — **чистая статика**: `.html`, `.css`, `.js`, картинки.
Без бэкенда. Если попался проект, который надо собирать через `npm run build` —
либо собери и возьми папку с результатом, либо возьми другой.

**2. Создать** проект на гитхабе или сделать ветку от этого проекта и разместить директории lesson-2

**3. Открыть `index.html` двойным кликом** — убедиться, что сайт вообще живой,
до всякого докера.

**4. Написать свой Dockerfile.** Сайт уже готовая статика — значит этап сборки
не нужен, хватит одного `FROM nginx`. Это будет сильно короче нашего.

**5. Написать свой `site.conf`** под этот сайт. Посмотри, как он устроен:
где лежит `index.html`, есть ли вложенные папки, есть ли страница 404.

**6. Собрать и запустить.**

**7. Проверить**
