# 3. Операции с подами

В задании написано «контейнеры», но в Kubernetes работаем с подами. Под содержит один или несколько контейнеров, и почти все команды kubectl принимают имя пода. Если контейнеров в поде несколько, нужный выбирается флагом `-c <контейнер>`

Для тех, кто знаком с Docker:

| Задача | Docker | Kubernetes |
|---|---|---|
| список | `docker ps` | `kubectl get pods` |
| подробности | `docker inspect` | `kubectl describe pod` |
| утилизация | `docker stats` | `kubectl top pods` |
| логи | `docker logs` | `kubectl logs` |
| зайти внутрь | `docker exec -it` | `kubectl exec -it` |
| остановить | `docker stop` | `kubectl scale --replicas=0` |

Имена подов длинные (`web-7d4b9c8f5-x2k9p`), их берём из `kubectl get pods`. Вместо имени пода можно писать `deploy/<имя>`, тогда kubectl сам выберет один под этого деплоймента

## Проверить состояние

```bash
kubectl get pods
```

Список подов в текущем namespace

| Столбец | Что значит |
|---|---|
| `READY` | сколько контейнеров пода готово из общего числа |
| `STATUS` | `Running`, `Pending` (ждёт ноду или диск), `ContainerCreating` (качает образ), `CrashLoopBackOff` (контейнер падает и перезапускается), `ImagePullBackOff` (не может скачать образ) |
| `RESTARTS` | сколько раз контейнер перезапускался; растёт значит падает |
| `AGE` | сколько живёт под |

```bash
kubectl get pods -o wide
```

То же плюс IP пода и нода, на которой он запущен

```bash
kubectl get pods -A
```

Поды во всех namespace, включая системные (`kube-system`)

```bash
kubectl describe pod <под>
```

Всё о поде: образ, переменные, тома, лимиты. Самое полезное в конце, блок `Events`: там написано, почему под не стартует (не скачался образ, не хватило памяти, не подключился диск)

```bash
kubectl get events --sort-by=.lastTimestamp
```

События по всему namespace по времени. Первое, куда смотреть, когда непонятно, что сломалось

## Посмотреть утилизацию

```bash
kubectl top pods
kubectl top pods --containers
kubectl top nodes
```

CPU и память по подам, по контейнерам внутри подов и по нодам. Работает только с включённым `metrics-server` из пункта 1

| Единица | Что значит |
|---|---|
| `250m` CPU | 250 милликор, четверть одного ядра |
| `512Mi` | 512 мебибайт памяти |

---

## Посмотреть логи

```bash
kubectl logs <под>
```

stdout и stderr главного процесса контейнера, как `docker logs`

| Флаг | Что делает |
|---|---|
| `-f` | следить за логом в реальном времени |
| `--tail=50` | последние 50 строк |
| `--since=10m` | за последние 10 минут |
| `--previous` | лог предыдущего запуска контейнера; нужен при `CrashLoopBackOff`, чтобы увидеть, почему он упал |
| `-c <контейнер>` | лог конкретного контейнера в поде |
| `-l app=mysql` | логи всех подов с меткой |

```bash
kubectl logs deploy/mysql --tail=20
```

## Подключиться к контейнеру

```bash
kubectl exec -it <под> -- bash
```

Открывает shell внутри контейнера. Всё после `--` это команда, которая выполнится в контейнере. Если `bash` не найден, в образе его нет, пробуй `sh`

```bash
kubectl exec <под> -- cat /etc/os-release
```

Одна команда без интерактивного shell

```bash
kubectl port-forward <под> 8080:80
```

Пробрасывает порт пода на локальную машину, чтобы постучаться в приложение снаружи

## Остановить

В Kubernetes нет команды «остановить под». Deployment следит за числом подов и сразу поднимает удалённый заново

```bash
kubectl delete pod <под>
```

Удаляет под, Deployment тут же создаёт новый с другим именем. Так перезапускают зависшее приложение

```bash
kubectl scale deploy/mysql --replicas=0
```

Настоящая остановка: Deployment остаётся, подов ноль. Диск PVC и Secret на месте

```bash
kubectl scale deploy/mysql --replicas=1
```

Запустить обратно, данные mysql сохранились на PVC

| Команда | Что делает |
|---|---|
| `kubectl rollout restart deploy/<имя>` | перезапустить все поды по очереди |
| `kubectl delete -f mysql.yaml` | удалить всё, что создано из файла |
| `helm uninstall web` | удалить Helm-релиз |
| `kubectl delete deploy wildfly` | удалить деплоймент и его поды |
| `minikube stop` | остановить весь кластер |
