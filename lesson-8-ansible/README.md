# Урок 8. Ansible

В уроках 3–7 сервер готовился руками: поставить Docker, склонировать репозиторий, положить `.env`, поднять compose. Всё это живёт в твоей памяти и в истории терминала. Умрёт виртуалка, и придётся вспоминать, в каком порядке что делалось и какой там был пароль

Ansible описывает сервер кодом. Одна команда приводит чистую виртуалку к рабочему состоянию, повторный запуск на готовой ничего не меняет. В уроке SSH и inventory, плейбук, задачи и модули, роли, идемпотентность, секреты и перенос ручного деплоя из прошлых уроков в плейбук

---

## 1. Как ansible ходит на сервер

Ansible запускается у тебя на машине и ходит на сервер по тому же SSH, которым ты пользовался с урока 3. На сервере ничего ставить не нужно, кроме python, а он есть в любой Ubuntu из коробки

На каждую задачу ansible делает одно и то же: копирует по SSH маленькую python-программу (модуль), запускает её на сервере и забирает ответ в JSON. В ответе главное поле `changed`: поменял модуль что-то на сервере или всё уже было как надо

| Термин | Что это |
|---|---|
| control node | машина, где запускается ansible. Твой ноутбук, в уроке 9 раннер GitHub |
| managed node | сервер, которым управляют |
| модуль | программа, которая умеет одно дело: файл, пакет, сервис, compose |
| задача (task) | вызов модуля с параметрами |
| плейбук (playbook) | список задач для группы серверов |

Установка:

```bash
pipx install --include-deps ansible
ansible --version
```

Пакет `ansible` приносит сам `ansible-core` и набор коллекций модулей, в том числе `community.docker`, который понадобится в пункте 6

**На Windows ansible не работает**, только через WSL. Проект при этом удобно держать на диске `C:`, и тут первая грабля: WSL показывает файлы с `C:` с правами `777`, и ansible отказывается читать `ansible.cfg` из такой папки:

```
[WARNING]: Ansible is being run in a world writable directory (...), ignoring it as an ansible.cfg source.
```

Лечится один раз: в `/etc/wsl.conf` внутри WSL добавить

```ini
[automount]
options = "metadata,umask=22,fmask=11"
```

и из Windows выполнить `wsl --shutdown`. После перезапуска файлы на `C:` получают нормальные права. На это наступили в живом проекте, когда переносили плейбуки из домашней папки WSL в репозиторий

## 2. Inventory и первая команда

Все файлы урока лежат в [ansible/](ansible/), команды запускаются оттуда

[inventory.ini](ansible/inventory.ini) это список серверов:

```ini
[app]
vm ansible_host=203.0.113.10 ansible_user=ubuntu
```

| Часть | Что значит |
|---|---|
| `[app]` | группа. Плейбук говорит «на группу app», и не знает, сколько там машин |
| `vm` | имя хоста для ansible, им он подписывает вывод |
| `ansible_host` | куда ходить по SSH, IP твоей виртуалки |
| `ansible_user` | под кем заходить. Тот же пользователь, под которым ты заходил руками |

[ansible.cfg](ansible/ansible.cfg) избавляет от `-i inventory.ini` в каждой команде:

```ini
[defaults]
inventory = inventory.ini
```

Проверка связи:

```bash
ansible app -m ping
```

`-m ping` это модуль, который ничего не делает, только проверяет, что ansible зашёл по SSH и нашёл python. Ответ с живого сервера:

```json
{"ansible_facts": {"discovered_interpreter_python": "/usr/bin/python3.14"},
 "changed": false,
 "ping": "pong"}
```

`pong` значит, что вся цепочка работает: inventory, SSH-ключ, python на сервере. `changed: false`, потому что `ping` ничего не меняет

Любой модуль можно вызвать так же, одной командой, без плейбука:

```bash
ansible app -a "uptime"
ansible app -b -a "docker ps"
```

`-a` без `-m` запускает команду модулем `command`. `-b` (become) выполняет её через `sudo`

## 3. Первый плейбук: Docker

Руками в уроке 3 это было так:

```bash
curl -fsSL https://get.docker.com | sh
```

В ansible то же самое в роли [docker](ansible/roles/docker/tasks/main.yml):

```yaml
- name: Скачать установщик Docker
  ansible.builtin.get_url:
    url: https://get.docker.com
    dest: /root/get-docker.sh
    mode: "0755"

- name: Поставить Docker, если его ещё нет
  ansible.builtin.command: sh /root/get-docker.sh
  args:
    creates: /usr/bin/docker

- name: Docker запущен и стартует после ребута
  ansible.builtin.systemd_service:
    name: docker
    state: started
    enabled: true
```

Три задачи, три разных модуля. Каждая описывает **состояние**, к которому надо прийти:

| Задача | Состояние | Что будет на втором прогоне |
|---|---|---|
| `get_url` | файл `/root/get-docker.sh` лежит на месте | файл уже есть, модуль его не трогает, `ok` |
| `command` с `creates` | `/usr/bin/docker` существует | файл есть, команда не запускается, `skipped` |
| `systemd_service` | сервис запущен и в автозапуске | уже так, `ok` |

Это и есть идемпотентность: первый прогон делает работу, второй видит, что делать нечего. Один и тот же плейбук годится и для чистой машины, и для настроенной

У модуля `command` своего понимания состояния нет. Ansible не знает, что делает произвольная команда, и считает, что она всегда что-то меняет. `creates` добавляет ему это знание: есть файл, значит работа сделана. Без `creates` установщик Docker запускался бы на каждом прогоне

Правило, которое отсюда следует: сначала ищешь модуль под задачу (файл, пакет, сервис, compose), и только если его нет, берёшь `command` и сам объясняешь ansible, когда команда что-то меняет

В живом проекте подготовка сервера под Arch Linux сложнее: обновление системы, ребут, замена `iptables`. Весь этот блок пропускается на уже настроенной машине одной проверкой:

```yaml
- name: Gather installed package facts
  ansible.builtin.package_facts:
    manager: pacman

- name: Bootstrap fresh VM (only when docker is not yet installed)
  when: "'docker' not in ansible_facts.packages"
  block:
    - name: Full system upgrade
      community.general.pacman:
        update_cache: true
        upgrade: true
```

`package_facts` собирает список пакетов, `block` группирует задачи, `when` на блоке решает за все сразу. Цена приёма: признак «стоит docker» заменяет проверку каждого шага. Если прогон упадёт между установкой пакета и запуском сервиса, следующий прогон увидит docker и пропустит весь блок, включая недоделанный запуск. Задачи, которые сами идемпотентны, как три задачи выше, такой страховки не требуют

## 4. Роли и одна точка входа

Задач становится много, и их раскладывают по ролям: папка на одну тему со стандартной структурой

```
ansible/
├── ansible.cfg
├── inventory.ini
├── requirements.yml
├── site.yml                 единственная точка входа
├── secrets.env.example
├── group_vars/
│   └── all.yml              переменные проекта
└── roles/
    ├── docker/
    │   └── tasks/main.yml   поставить и запустить Docker
    └── app/
        ├── defaults/main.yml    значения по умолчанию
        ├── tasks/main.yml       выкатить проект
        └── templates/env.j2     шаблон .env
```

[site.yml](ansible/site.yml):

```yaml
- name: Сервер с проектом
  hosts: app
  become: true
  roles:
    - docker
    - app
```

`become: true` выполняет все задачи через `sudo`: ставить пакеты и писать в `/opt` обычный пользователь не может

Точка входа одна, и запускается она всегда целиком, на свежей машине и на рабочей. Так же устроено в живом проекте:

```yaml
- name: Converge VM and deploy the app
  hosts: ec_instances
  roles:
    - role: prepare_vm
      tags: [prepare]
    - role: deploy
      tags: [deploy]
```

Никаких «сначала прогони вот это руками, потом вот это». `tags` там позволяют запустить часть: `ansible-playbook site.yml --tags deploy` пропустит подготовку сервера

## 5. Переменные и секреты

Переменные лежат в трёх местах, и чем ниже в таблице, тем сильнее:

| Где | Для чего | В уроке |
|---|---|---|
| `roles/app/defaults/main.yml` | разумные значения роли, которые можно перебить | `app_dir`, `http_port` |
| `group_vars/all.yml` | настройки проекта | `app_image`, имена базы, пароль |
| `-e` в командной строке | значение на один запуск | `app_tag` |

`all.yml` читается для всех хостов. Если назвать файл по группе, `group_vars/app.yml`, он будет читаться только для группы `app`, и имя должно совпадать с `[app]` в inventory буква в букву

Версия приходит через `-e app_tag=v1.2.0`, потому что меняется на каждом деплое. Держать её в файле значит коммитить на каждый релиз

Пароль в git класть нельзя. В [group_vars/all.yml](ansible/group_vars/all.yml) он читается из окружения того, кто запускает плейбук:

```yaml
postgres_password: "{{ lookup('env', 'POSTGRES_PASSWORD') | trim }}"
```

Локально окружение наполняется из `secrets.env`, который лежит в `.gitignore`:

```bash
cp secrets.env.example secrets.env
set -a; source secrets.env; set +a
```

`set -a` нужен обязательно. Без него `source` создаёт переменные в текущем shell, но не экспортирует их, ansible запускается дочерним процессом и их не видит

У `lookup('env', ...)` неприятное свойство: незаданная переменная даёт пустую строку, без ошибки. Пустой пароль отрендерился бы в `.env`, и сломалось бы всё где-то дальше. Поэтому первая задача роли `app` проверяет входные данные:

```yaml
- name: Версия и пароль заданы
  ansible.builtin.assert:
    that:
      - app_tag is defined
      - postgres_password | length > 0
    fail_msg: >-
      Нужны -e app_tag=vX.Y.Z и POSTGRES_PASSWORD в окружении.
      Локально: set -a; source secrets.env; set +a
    quiet: true
```

Плейбук падает на первой же задаче с понятным текстом и ничего не успевает тронуть. Приём взят из живого проекта, там так проверяются пять секретов. Там же в `group_vars` список секретов виден целиком, а значений нет:

```yaml
ec_bot_token: "{{ lookup('env', 'BOT_TOKEN') | trim }}"
ec_s3_access_key: "{{ lookup('env', 'S3_ACCESS_KEY') | trim }}"
ec_s3_secret_key: "{{ lookup('env', 'S3_SECRET_KEY') | trim }}"
```

`trim` там появился после реальной поломки: файл с секретами был сохранён с Windows-переводами строк, ключ S3 приезжал с хвостовым `\r`, и хранилище отвечало, что такого ключа не существует

Почему не `ansible-vault`, который шифрует секреты прямо в репозитории. В живом проекте его рассмотрели и отказались: пароль от vault всё равно пришлось бы положить в секреты GitHub, иначе пайплайн его не расшифрует. Хранилище секретов уже есть, второй слой шифрования поверх него добавляет обряд с `ansible-vault edit` и нечитаемые диффы, а защиты почти не добавляет

## 6. Роль app: перенос ручного деплоя

| Руками в уроках 3–7 | Задача в [roles/app/tasks/main.yml](ansible/roles/app/tasks/main.yml) |
|---|---|
| `git clone` на сервер | `file` + `copy`: на сервер едут только `docker-compose.yml` и `nginx/site.conf` |
| `cp .env.example .env` и правка руками | `template` из [env.j2](ansible/roles/app/templates/env.j2) |
| `docker compose up -d` | модуль `community.docker.docker_compose_v2` |

Копирование:

```yaml
- name: docker-compose.yml и конфиг nginx
  ansible.builtin.copy:
    src: "{{ playbook_dir }}/../{{ item }}"
    dest: "{{ app_dir }}/{{ item }}"
    mode: "0644"
  loop:
    - docker-compose.yml
    - nginx/site.conf
```

`loop` повторяет задачу для каждого элемента списка, текущий элемент лежит в `item`. `playbook_dir` это папка, где лежит `site.yml`, значит `..` это корень проекта. `copy` сравнивает файл на сервере с твоим и перезаписывает, только если они разные

Исходники на сервер больше не едут. Сервер получает ровно то, что нужно для запуска: compose, конфиг и `.env`. Git, токен к репозиторию и клон с историей ему не нужны

`.env`:

```yaml
- name: .env с версией и паролем
  ansible.builtin.template:
    src: env.j2
    dest: "{{ app_dir }}/.env"
    mode: "0600"
  diff: false
```

`template` отличается от `copy` тем, что прогоняет файл через шаблонизатор Jinja2 и подставляет переменные вместо `{{ }}`. `mode: "0600"` делает файл читаемым только для владельца, по умолчанию он был бы открыт на чтение всем. `diff: false` не даёт паролю попасть в вывод, если запустить плейбук с `--diff`

Запуск стека:

```yaml
- name: Поднять стек
  community.docker.docker_compose_v2:
    project_src: "{{ app_dir }}"
    pull: missing
    wait: true
    wait_timeout: 120
```

| Параметр | Что значит |
|---|---|
| `project_src` | папка с `docker-compose.yml`, как `cd` перед `docker compose up` |
| `pull: missing` | качать только те образы, которых нет на сервере. Тег неизменяемый, урок 7: если `v1.2.0` уже скачан, он тот самый |
| `wait: true` | то же, что `--wait`: ждать `healthy` и падать, если не дождались |

Модуль честно отвечает, поменял ли он что-то: пересоздал контейнеры, значит `changed`, всё уже крутилось с нужными параметрами, значит `ok`. Модуль ставится из [requirements.yml](ansible/requirements.yml):

```bash
ansible-galaxy collection install -r requirements.yml
```

В живом проекте compose запускается через `command`, и деплой устроен как переустановка: остановить всё, стереть папку, скопировать файлы заново, поднять стек. Каждый прогон перезапускает все контейнеры, даже если не поменялось ничего, и в отчёте всегда `changed`. Для одного релиза в день это допустимо, но так теряется главный сигнал ansible: по отчёту уже не видно, что реально изменилось. С модулем повторный прогон той же версии не трогает ни один контейнер

## 7. Запуск и идемпотентность

Из папки `ansible/`:

```bash
ansible-galaxy collection install -r requirements.yml
set -a; source secrets.env; set +a
ansible-playbook site.yml -e app_tag=v1.2.0
```

В конце прогона ansible печатает итог по каждому хосту, строку `PLAY RECAP`:

| Поле | Что значит |
|---|---|
| `ok` | задача выполнена, менять было нечего |
| `changed` | задача что-то поменяла на сервере |
| `skipped` | задача пропущена по условию, как `command` с `creates` |
| `failed` | задача упала, дальше на этом хосте ничего не выполнялось |
| `unreachable` | до хоста не достучались по SSH |

Первый прогон на чистой машине: `changed` у скачивания установщика, установки Docker, каталога, файлов, `.env` и запуска стека. Второй прогон той же командой должен дать `changed=0`. Это главная проверка плейбука: если на втором прогоне что-то `changed`, значит задача описывает действие там, где должна описывать состояние

Новая версия это та же команда с другим тегом. Поменяется одна строка в `.env`, модуль compose пересоздаст `backend`, остальное останется `ok`

Сухой прогон показывает, что поменялось бы, ничего не меняя:

```bash
ansible-playbook site.yml -e app_tag=v1.3.0 --check --diff
```

`--diff` покажет разницу в `docker-compose.yml` и конфиге nginx. `.env` он не покажет из-за `diff: false`

## 8. Переезд с ручного деплоя

На сервере уже крутится проект из урока 7, в `~/app`. Плейбук выкатывает в `/opt/events`, и тут две грабли, на которые наступаешь гарантированно

**Порт занят.** Старый стек держит порт 80, новый не сможет его занять. Старый стек нужно остановить, без `-v`, иначе удалятся данные:

```bash
cd ~/app && docker compose down
```

**База окажется пустой.** Compose называет проект по имени папки, и volume с базой тоже: в `~/app` это `app_pgdata`. В [docker-compose.yml](docker-compose.yml) урока имя проекта задано явно:

```yaml
name: events
```

С ним volume называется `events_pgdata` при любой папке. Старые данные лежат в `app_pgdata`, и новый стек их не увидит. Перенеси их дампом и восстановлением из урока 6: дамп со старого стека до `down`, восстановление в новый после первого прогона плейбука. Или впиши в `name:` имя старой папки, и compose подхватит старый volume

В живом проекте `name:` добавили ровно из-за этого, когда деплой переезжал на ansible: стек раскатывается в новую папку, и без явного имени мониторинг и прокси молча начали бы с пустыми volume

## 9. Что видно, когда сломалось

| Что в выводе | Причина |
|---|---|
| `UNREACHABLE! ... Permission denied (publickey)` | неверный `ansible_user` или ключ не лежит в `authorized_keys` этого пользователя |
| `Missing sudo password` | `sudo` на сервере просит пароль. Запусти с `-K`, ansible спросит его один раз |
| `couldn't resolve module/action 'community.docker.docker_compose_v2'` | коллекция не установлена, `ansible-galaxy collection install -r requirements.yml` |
| `Assertion failed` и текст про `app_tag` | забыл `-e app_tag=...` или `set -a; source secrets.env` |
| `ignoring it as an ansible.cfg source` | WSL и файлы на `C:`, пункт 1 |
| `port is already allocated` | старый стек держит порт, пункт 8 |
| `password authentication failed` в логе `backend` | пароль в `secrets.env` не совпадает с тем, с которым база создавалась. Пароль Postgres читает только при первом запуске, урок 6 |

## 10. Практика: поднять проект на чистой машине

**Легенда.** Старая виртуалка умерла, выдали новую, чистую Ubuntu. Проект должен подняться одной командой с твоего ноутбука. Потом той же командой переводишь на ansible и рабочий сервер

### Что сделать

**1. Ansible в проекте.** Папка `ansible/` рядом с `docker-compose.yml`: inventory, cfg, `site.yml`, две роли. Секреты в `secrets.env` вне git

**2. Чистая машина.** Возьми новую виртуалку, без Docker и без проекта. `ansible app -m ping` отвечает `pong`

**3. Один прогон.** `ansible-playbook site.yml -e app_tag=<версия из урока 7>` ставит Docker, раскладывает файлы, поднимает стек. `curl http://<IP>/health` отвечает с нужной версией

**4. Второй прогон.** Та же команда, в `PLAY RECAP` `changed=0`. Если нет, найди задачу, которая врёт, и исправь

**5. Новая версия.** Прогон с другим тегом меняет только `.env` и контейнер приложения. Покажи, какие задачи были `changed`

**6. Проверка assert.** Запусти без `secrets.env` и без `-e app_tag`. Плейбук должен упасть на первой задаче с понятным текстом
