# Урок 7. CI/CD на GitHub Actions

До этого урока выкатка была ручной: зайти на сервер, `git pull`, `docker compose up -d --build`. Образ собирался прямо на виртуалке, и что именно там крутится, знал только тот, кто последним набирал команды

Здесь сборка уезжает в GitHub Actions. Образ собирается один раз, получает версию, уезжает в registry, а сервер его только скачивает. В уроке workflow и триггеры по веткам и тегам, линт, сборка и пуш образа в Docker Hub, секреты, деплой по SSH и откат на прошлую версию одной кнопкой

В уроках 7–9 рядом с учебным кодом разбирается живой проект: Telegram-бот на Python и бэкенд на Go с MongoDB, мониторингом и S3, всё на одной виртуалке. Его репозитории закрыты, нужные куски приведены прямо здесь

## 1. Что меняется

| | Уроки 3–6 | Этот урок |
|---|---|---|
| Где собирается образ | на сервере, `--build` при каждом деплое | на раннере GitHub, один раз на версию |
| Что нужно серверу | исходники, токен к репозиторию, время и память на сборку | `docker-compose.yml`, `.env` и доступ к registry |
| Что такое версия | то, что лежало в `main` в момент `git pull` | git-тег `v1.2.0`, тот же тег у образа и в `/health` |
| Откат | `git checkout` на сервере и пересборка | запуск деплоя со старым тегом, образ уже лежит в registry |
| Кто проверяет код | никто | линтер на каждый пуш |

CI (continuous integration) это проверки и сборка на каждое изменение. CD (continuous delivery) это доставка собранного на сервер. Вместе они называются пайплайном: цепочка шагов от пуша до работающего сервиса

## 2. Workflow

Пайплайн в GitHub Actions описывается YAML-файлами в папке `.github/workflows/` в корне репозитория. GitHub сам находит их и запускает на нужные события. В этом уроке файлы лежат в [.github/workflows/](.github/workflows/) папки урока, в свой проект их копируешь в корень

Самая маленькая джоба из [pipeline.yml](.github/workflows/pipeline.yml), линт:

```yaml
jobs:
  lint:
    runs-on: ubuntu-latest
    container: python:3.13-slim
    steps:
      - uses: actions/checkout@v5
      - run: pip install ruff==0.16.9
      - run: ruff check backend
```

| Ключ | Что значит |
|---|---|
| `jobs` | джобы пайплайна. Без `needs` они идут параллельно |
| `runs-on` | на какой машине запускать. `ubuntu-latest` это чистая виртуалка GitHub, живёт одну джобу и потом выбрасывается |
| `container` | запустить шаги внутри этого образа. Без ключа они идут прямо на виртуалке |
| `steps` | шаги по порядку. Упал шаг, упала джоба, остальные шаги не выполняются |
| `uses` | готовое действие (action) из маркетплейса. `actions/checkout` скачивает код репозитория |
| `run` | обычная shell-команда |

Раннер каждый раз чистый, поэтому каждая джоба начинает с `checkout`: кода на машине нет, пока его не скачали

Почему линт идёт в `python:3.13-slim`: это тот же образ, на котором собирается [backend/Dockerfile](backend/Dockerfile). Линтер смотрит на код глазами той версии языка, на которой код будет работать в проде. В живом проекте так же, линт бота гоняется в образе из его Dockerfile:

```yaml
jobs:
  lint:
    runs-on: ubuntu-latest
    container: ${{ inputs.base_image }}
    steps:
      - uses: actions/checkout@v5
      - run: pip install ruff
      - run: ruff check .
```

Здесь `ruff` ставится без версии. Новый релиз линтера может включить новые правила, и пайплайн покраснеет без единого изменения в коде. Поэтому в уроке версия прибита: `ruff==0.16.9`

Что видно, когда линт нашёл ошибку:

```
F401 [*] `os` imported but unused
 --> bad.py:1:8
  |
1 | import os
  |        ^^
help: Remove unused import: `os`

Found 1 error.
```

Код выхода ненулевой, шаг красный, дальше пайплайн не идёт. Тот же `ruff check backend` можно запустить у себя до пуша

## 3. Триггеры: ветки и теги

Весь пайплайн урока это два файла:

| Файл | Когда запускается | Что делает |
|---|---|---|
| [pipeline.yml](.github/workflows/pipeline.yml) | пуш в любую ветку и пуш тега `v*` | линт, а для тега ещё сборка и деплой |
| [deploy.yml](.github/workflows/deploy.yml) | вызов из `pipeline.yml` или кнопка Run workflow | выкатывает на сервер указанную версию |

Триггеры в `pipeline.yml`:

```yaml
on:
  push:
    branches: ["**"]
    tags: ["v*"]
```

| Событие | Что запускается |
|---|---|
| `git push` ветки | только `lint` |
| `git push origin v1.2.0` | `lint` → `build` → `deploy` |
| кнопка Run workflow у `deploy` | только деплой, сборки нет |

Сборка отсекается условием `if: github.ref_type == 'tag'` у джобы `build`. У `deploy` стоит `needs: build`, и если `build` пропущен, деплой пропускается вместе с ним

Релиз выглядит так:

```bash
git tag v1.2.0
git push origin v1.2.0
```

**Грабли.** Если в `on.push` написать только `branches`, пуши тегов пайплайн запускать перестанут. GitHub читает фильтры буквально: не указаны теги, значит на теги не реагируем. Нужны оба ключа, как выше

### Как это сделано в живом проекте

Там другой подход к релизу. Обёртка в репозитории бота:

```yaml
on:
  push:
    branches-ignore: [main]
  workflow_dispatch:
    inputs:
      tag:
        required: false

jobs:
  pipeline:
    uses: <org>/pipelines/.github/workflows/pipeline.yml@main
    with:
      language: python
      base_image: python:3.12-slim
      tag: ${{ inputs.tag }}
      dockerhub_image: <login>/telegram-bot
      infra_repository: <org>/infra
    secrets: inherit
```

Пуш в ветку гоняет только линт. Сборка и выкатка запускаются кнопкой, тег образа вписывается руками в форму запуска. Ветку выкатывают в прод и проверяют там **до** мержа в `main`, а сам мерж ничего не запускает. Автор называет это deploy-before-merge: ветка сначала доказывает себя в проде, день ожидания входит в процесс

Цена такого решения: git-тег ставится руками после мержа, а тег образа вписывается руками при сборке, и их совпадение держится на человеке. В живом проекте один образ так и ушёл в прод с тегом, которого в git нет. В схеме урока тег образа берётся из `github.ref_name`, то есть из самого git-тега, и разойтись они не могут

### Модели ветвления

То, как в команде устроены ветки и откуда идёт релиз, называется флоу (branching model). На собеседовании и в первую неделю на новой работе спросят, какой у вас флоу, и будут ждать знакомых слов. Основных четыре:

| Флоу | Ветки | Как идёт релиз | Где встречается |
|---|---|---|---|
| Git Flow | `main`, `develop`, `feature/*`, `release/*`, `hotfix/*` | из `develop` отрезается `release/1.4`, стабилизируется, вливается в `main` и получает тег | большие команды с релизами по графику, мобильные и коробочные продукты, где в поддержке несколько версий сразу |
| GitHub Flow | `main` и короткие ветки под задачу | ветка → pull request с ревью → мерж в `main` → деплой `main` | большинство веб-сервисов, небольшие и средние команды |
| GitLab Flow | `main` плюс ветки окружений, например `pre-production` и `production` | мерж в `main`, потом перенос дальше по веткам окружений | выкатка в прод по окнам или с ручным подтверждением |
| Trunk-based | все работают в `main`, ветки живут день-два | `main` всегда готов к выкатке, недоделанное прячется за фича-флагами | команды с хорошими автотестами и деплоями по много раз в день |

Флоу этого урока это GitHub Flow с релизом по тегу: ветки сливаются в `main`, тег на `main` запускает сборку и деплой

Словарь, который встретится в любой команде:

| Термин | Что это |
|---|---|
| фича-ветка, `feature/*` | ветка под одну задачу, живёт, пока задача не влита |
| `develop` | в Git Flow ветка интеграции: туда сливаются фичи, из неё режутся релизы. В `main` попадают только релизы |
| релизная ветка, `release/*` | заморозка перед релизом: новых фич нет, только исправления |
| хотфикс, `hotfix/*` | срочное исправление прода. Отрезается от того, что сейчас в проде, выкатывается вне очереди фич и вливается обратно, чтобы не потеряться в следующем релизе |
| pull request, merge request | запрос на мерж ветки с ревью. На GitHub PR, на GitLab MR, суть одна |
| защищённая ветка | пушить в неё напрямую нельзя, только через PR с зелёными проверками |
| cherry-pick | перенести отдельный коммит в другую ветку |
| фича-флаг | выключатель в конфиге: код уже в проде, а функция включается позже |
| semver, `vMAJOR.MINOR.PATCH` | MAJOR ломает совместимость, MINOR добавляет функцию, PATCH исправляет |

Хотфикс в Git Flow, где в `main` лежит прод, а в `develop` уже следующий релиз:

```bash
git switch -c hotfix/1.4.1 main
# исправление и коммит
git switch main
git merge --no-ff hotfix/1.4.1
git tag v1.4.1
git switch develop
git merge --no-ff hotfix/1.4.1
```

Второй мерж в `develop` забывают чаще всего, и следующий релиз снова приносит в прод ту же ошибку. В GitHub Flow хотфикс от обычной задачи отличается только срочностью: в `main` и так лежит то, что в проде

**Почему в живом проекте deploy-before-merge.** Флоу подбирается под команду и продукт:

| Условие проекта | Что из него следует |
|---|---|
| один-два разработчика, в репозитории одна активная ветка | `develop` и релизные ветки Git Flow вести некому, это ритуал без пользы |
| staging нет, прод единственное окружение | проверить ветку можно только в проде. Её выкатывают до мержа, а в `main` попадает только проверенное |
| пользователей несколько человек в день | ошибка в проде стоит дёшево, день в проде и есть тестирование |
| в пайплайне только линт, автотестов нет | trunk-based без тестов означает регулярно ломать `main` |
| сервисы в отдельных репозиториях, версии независимы | общего графика релизов нет, у каждого сервиса свой короткий цикл |

Шаг Deploy перед Merge стоял и в старом описании GitHub Flow на сайте GitHub, так что схема не самодельная. Её предел тоже известен: две ветки нельзя проверять в проде одновременно, вторая выкатка затрёт первую. Пока разработчик один, этого не видно. При трёх-пяти людях появляется очередь на прод, и тогда нужен staging и переход на «мерж, потом деплой». Git Flow появляется, когда у продукта график релизов или несколько версий в поддержке, например мобильное приложение, которое пользователи обновляют не сразу. Сам автор Git Flow в 2020 году дописал к своей статье, что для веб-приложений с непрерывной доставкой лучше брать модель попроще

## 4. Версия внутри образа

Чтобы после деплоя и отката проверить, что выкатилось, приложение должно уметь назвать свою версию. Это решение разработчика, но нужно оно в первую очередь тому, кто выкатывает

Версию передаёт пайплайн при сборке, в [backend/Dockerfile](backend/Dockerfile) она превращается в переменную окружения:

```dockerfile
COPY . .

ARG APP_VERSION=dev
ENV APP_VERSION=${APP_VERSION}
```

| Строка | Что делает |
|---|---|
| `ARG APP_VERSION=dev` | принимает `--build-arg APP_VERSION=v1.2.0`. Без аргумента будет `dev`, так видно, что образ собран руками |
| `ENV APP_VERSION=${APP_VERSION}` | кладёт значение в окружение контейнера, оттуда его читает приложение |

`ARG` стоит после `COPY`, а `pip install` выше обоих. Каждая сборка приходит с новой версией, и всё, что ниже `ARG`, пересобирается. Зависимости выше, их слой берётся из кэша

Дальше [config.py](backend/source/config.py) читает переменную, а `/health` в [handlers/system.py](backend/source/handlers/system.py) отдаёт её наружу:

```
$ curl -s http://localhost:8080/health
{"limit":100,"status":"ok","stored":2,"version":"v1.2.0"}
```

Собрать то же самое у себя:

```bash
docker build --build-arg APP_VERSION=v1.0.0 -t events:v1.0.0 backend
docker run --rm events:v1.0.0 printenv APP_VERSION
```

```
v1.0.0
```

В живом проекте версия в образ не вшивается: `/health` бэкенда отдаёт очереди и воркеры, логи старта про версию молчат. Что крутится в проде, видно только по тегу образа в `docker ps`. Вшить её в Go можно флагом `go build -ldflags "-X main.version=v0.3.10"` и отдавать в `/health` так же, как здесь

## 5. Сборка и пуш образа

Registry это склад образов: пайплайн туда кладёт, сервер оттуда забирает. В уроке Docker Hub, как в живом проекте

**Docker Hub**: зарегистрироваться, дальше **Account settings → Personal access tokens → Generate new token**, права **Read & Write**. Токен показывается один раз. Пароль от аккаунта в пайплайн не кладём: токен можно отозвать отдельно и ограничить правами

Джоба `build` из [pipeline.yml](.github/workflows/pipeline.yml):

```yaml
  build:
    needs: lint
    if: github.ref_type == 'tag'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: docker/setup-buildx-action@v3
      - uses: docker/login-action@v3
        with:
          username: ${{ vars.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}
      - uses: docker/build-push-action@v6
        with:
          context: backend
          build-args: APP_VERSION=${{ github.ref_name }}
          push: true
          tags: ${{ vars.DOCKERHUB_USERNAME }}/events:${{ github.ref_name }}
```

| Шаг | Что делает | Руками это было бы |
|---|---|---|
| `setup-buildx-action` | готовит сборщик buildx | ничего, локально он уже есть |
| `login-action` | логинится в Docker Hub | `docker login` |
| `build-push-action` | собирает и пушит | `docker build --build-arg ... -t ... backend` и `docker push ...` |
| `needs: lint` | сборка стартует только после зелёного линта | |
| `github.ref_name` | имя тега, на который пришёл пуш, например `v1.2.0` | |

Эта джоба почти дословно совпадает со сборкой в живом проекте:

```yaml
      - uses: actions/checkout@v5
      - uses: docker/setup-buildx-action@v3
      - uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}
      - uses: docker/build-push-action@v6
        with:
          file: ${{ inputs.dockerfile }}
          push: true
          tags: ${{ inputs.image_name }}:${{ inputs.tag }}
```

**Тег образа никогда не переписывается.** `v1.2.0` собран один раз и дальше означает ровно этот образ. На этом держится откат: деплой старого тега должен привезти тот самый старый код. Поэтому `latest` для деплоя не годится, завтра под ним будет другое. В схеме урока гарантию даёт git: запушить второй раз тот же тег он не даст без `--force`

## 6. Секреты и переменные

Пайплайну нужны доступы: токен Docker Hub, SSH-ключ от сервера, адрес сервера. В код их класть нельзя, для этого в репозитории есть хранилище: **Settings → Secrets and variables → Actions**, две вкладки

| Имя | Вкладка | Что там |
|---|---|---|
| `DOCKERHUB_TOKEN` | Secrets | токен Docker Hub из пункта 5 |
| `SSH_PRIVATE_KEY` | Secrets | приватный ключ для деплоя, пункт 7 |
| `DOCKERHUB_USERNAME` | Variables | логин на Docker Hub |
| `DEPLOY_HOST` | Variables | IP виртуалки |
| `DEPLOY_USER` | Variables | пользователь на виртуалке, под которым идёт деплой |
| `SSH_KNOWN_HOSTS` | Variables | публичный ключ сервера, пункт 7 |

| | Secrets | Variables |
|---|---|---|
| В workflow | `${{ secrets.ИМЯ }}` | `${{ vars.ИМЯ }}` |
| Прочитать после сохранения | нельзя, только перезаписать | можно |
| В логах пайплайна | заменяются на `***` | видны как есть |

Секретом делаешь только то, что даёт доступ. Логин и IP ни к чему не дают доступа, в Variables их видно и удобно править. Если сделать секретом логин Docker Hub, GitHub начнёт закрывать звёздочками все его упоминания в логах, включая имя образа

## 7. Деплой по SSH

### Подготовка сервера, один раз

На сервере из урока 3 уже лежит клон репозитория. В [docker-compose.yml](docker-compose.yml) урока у `backend` вместо `build` стоит образ:

```yaml
  backend:
    image: ${APP_IMAGE}:${APP_TAG}
```

Имя и версия приезжают из `.env`, поэтому в `.env` на сервере добавляются две строки:

```
APP_IMAGE=your-dockerhub-login/events
APP_TAG=v1.0.0
```

Дальше отдельный ключ, по которому пайплайн будет ходить на сервер. Генерируешь у себя, в `~/.ssh`, подальше от папки проекта:

```bash
ssh-keygen -t ed25519 -N '' -C github-actions -f ~/.ssh/ci_deploy
ssh-copy-id -i ~/.ssh/ci_deploy.pub <user>@<IP виртуалки>
cat ~/.ssh/ci_deploy
```

| Команда | Зачем |
|---|---|
| `-N ''` | ключ без пароля. Спросить пароль в пайплайне некому |
| `ssh-copy-id` | дописывает публичную часть в `~/.ssh/authorized_keys` на сервере |
| `cat` | вывод целиком, со строками `BEGIN` и `END`, уходит в секрет `SSH_PRIVATE_KEY` |

Ключ сервера для `SSH_KNOWN_HOSTS`:

```bash
ssh-keyscan -t ed25519 <IP виртуалки>
```

Строка вида `203.0.113.10 ssh-ed25519 AAAAC3...` целиком уходит в переменную. Когда ты первый раз заходил на сервер, ssh спросил «доверять ли этому ключу» и запомнил его в `~/.ssh/known_hosts`. Раннер каждый раз новый, спросить его некому, и без этой строки деплой упадёт на `Host key verification failed`

### Джоба деплоя

[deploy.yml](.github/workflows/deploy.yml), шаг с ключами:

```yaml
      - name: SSH-ключ и ключ сервера
        env:
          SSH_PRIVATE_KEY: ${{ secrets.SSH_PRIVATE_KEY }}
          SSH_KNOWN_HOSTS: ${{ vars.SSH_KNOWN_HOSTS }}
        run: |
          mkdir -p ~/.ssh
          echo "$SSH_KNOWN_HOSTS" >> ~/.ssh/known_hosts
          eval "$(ssh-agent -s)" > /dev/null
          echo "$SSH_PRIVATE_KEY" | ssh-add -
          echo "SSH_AUTH_SOCK=$SSH_AUTH_SOCK" >> "$GITHUB_ENV"
```

Приём взят из живого проекта один в один. Приватный ключ не пишется в файл на раннере: он сразу уходит в `ssh-agent`, и `ssh` берёт его оттуда. Последняя строка передаёт адрес агента следующим шагам: каждый `run` это новый процесс shell, и переменные между шагами сами не переезжают. Всё, что дописано в файл `$GITHUB_ENV`, появится в окружении следующих шагов

Шаг выкатки:

```yaml
      - name: Выкатить ${{ inputs.tag }}
        env:
          TAG: ${{ inputs.tag }}
          SERVER: ${{ vars.DEPLOY_USER }}@${{ vars.DEPLOY_HOST }}
        run: |
          ssh "$SERVER" bash -se <<EOF
            cd ~/app
            git pull -q
            sed -i '/^APP_TAG=/d' .env
            echo "APP_TAG=$TAG" >> .env
            docker compose up -d --pull always --wait
          EOF
```

Это те же команды, которые ты набирал руками, только набирает их раннер:

| Строка | Что делает |
|---|---|
| `bash -se <<EOF` | на сервере запускается bash и читает команды со входа. `-e` обрывает всё на первой ошибке |
| `git pull -q` | подтягивает свежий `docker-compose.yml` и конфиг nginx |
| `sed` и `echo` | заменяют строку `APP_TAG` в `.env` на новую версию |
| `--pull always` | скачать образы из registry, даже если такой тег уже лежит локально |
| `--wait` | дождаться, пока контейнеры станут `healthy`. Не дождались, команда падает, шаг красный |

`$TAG` подставляется ещё на раннере, до отправки на сервер. Тег приходит через `env`, в текст команды через `${{ }}` он не вклеивается: так содержимое поля не может превратиться в кусок shell-скрипта

`--wait` честен ровно настолько, насколько честен healthcheck. У `backend` в [docker-compose.yml](docker-compose.yml) он стучится в `/health`:

```yaml
    healthcheck:
      test: ["CMD", "python", "-c", "import urllib.request; urllib.request.urlopen('http://localhost:5000/health', timeout=2)"]
      interval: 5s
      timeout: 3s
      retries: 5
```

`/health` отвечает 503, если приложение не видит базу, `urlopen` на 503 бросает исключение, и проверка не проходит. Новая версия, которая не может подключиться к базе, не станет `healthy`, и пайплайн покраснеет. `curl` в образе нет, поэтому проверка на самом python

В живом проекте healthcheck есть только у MongoDB, у бэкенда и бота его нет. Там `--wait` ждёт только того, что процесс запустился, и упавший через секунду сервис деплой не поймает. Там же видно, почему проверку должен уметь проходить сам сервис: `/health` бэкенда всегда отвечает 200, даже когда база лежит

`concurrency: deploy` у джобы не даёт двум деплоям идти на сервер одновременно: второй ждёт, пока закончится первый

## 8. Откат

**Actions → deploy → Run workflow**, в поле `tag` старая версия, например `v1.1.0`

Сборки при этом нет: образ `v1.1.0` уже лежит в Docker Hub, деплой меняет строку в `.env` и поднимает контейнеры. Проверка:

```bash
curl -s http://<IP виртуалки>/health
```

В ответе `"version":"v1.1.0"`

Кнопка появляется благодаря `workflow_dispatch` в [deploy.yml](.github/workflows/deploy.yml). У того же файла второй вход, `workflow_call`, через него деплой зовёт `pipeline.yml` после сборки:

```yaml
on:
  workflow_call:
    inputs:
      tag:
        type: string
        required: true
  workflow_dispatch:
    inputs:
      tag:
        description: "Версия, которую выкатить, например v1.2.0"
        type: string
        required: true
```

```yaml
  deploy:
    needs: build
    uses: ./.github/workflows/deploy.yml
    with:
      tag: ${{ github.ref_name }}
    secrets: inherit
```

Деплой описан один раз, а входов у него два. `secrets: inherit` передаёт вызванному файлу секреты репозитория, без него `deploy.yml` получит пустой ключ

В живом проекте тем же механизмом (`uses` плюс `workflow_call`) весь конвейер вынесен в отдельный репозиторий `pipelines`: линт, сборка, деплой. Сервисов два, языки разные, а путь от пуша до прода одинаковый, поэтому в каждом сервисе лежит обёртка на двадцать строк с параметрами. Для одного проекта это лишнее, но стоит знать, что так бывает. Там ссылки идут на `@main`, и любая правка в библиотеке тут же меняет пайплайны всех сервисов, включая деплой в прод. Безопаснее ставить на библиотеку теги и ссылаться на `@v1`

### Что откат не откатывает

Откат возвращает код, данные остаются как есть. Если новая версия поменяла что-то в базе, старая версия увидит базу уже изменённой

В живом проекте бэкенд при каждом старте прогоняет миграции: дописывает недостающие поля, переписывает старые форматы. Одна из них переписала пути к фотографиям на новое хранилище. Старый образ после отката будет искать файлы по старым путям. Правило, которое отсюда следует: изменения в базе делаются так, чтобы предыдущая версия приложения с ними работала. Сначала выкатывается код, который понимает оба формата, и только следующим релизом старое убирается

## 9. Что видно, когда сломалось

| Где упало | Что в логе джобы | Причина |
|---|---|---|
| `lint` | `Found 1 error.` | ошибка линтера, выше в логе файл и строка |
| `build`, шаг логина | `unauthorized: incorrect username or password` | неверный `DOCKERHUB_USERNAME` или токен |
| `build`, пуш | `denied: requested access to the resource is denied` | токен без права Write или образ называется не твоим логином |
| `deploy` | `Host key verification failed.` | пустая или неверная `SSH_KNOWN_HOSTS` |
| `deploy` | `Permission denied (publickey)` | публичный ключ не дописан в `authorized_keys` пользователя `DEPLOY_USER` |
| `deploy`, `compose up` | `manifest unknown` | такого тега нет в registry, опечатка в теге или его сборка упала |
| `deploy`, `compose up` | контейнер `backend` `unhealthy` | новая версия не проходит `/health`. Смотри `docker compose logs backend` на сервере |

Во всех случаях первое действие одно: открыть упавший шаг в **Actions** и прочитать последние строки. Пайплайн показывает ровно тот вывод, который ты увидел бы, набирая эти команды руками

## 10. Практика: выкатка по тегу

**Легенда.** Проект живёт на виртуалке и выкатывается руками. Нужно, чтобы релиз был одной командой `git push origin v1.3.0`, а откат одной кнопкой. На сервере больше ничего не собирается

### Что сделать

**1. Линт на каждый пуш** в любую ветку. Версия линтера прибита, python в линте тот же, что в Dockerfile. Специально запушь ошибку и покажи красный пайплайн

**2. Версия в приложении.** Пайплайн вшивает git-тег в образ, эндпоинт здоровья отдаёт её наружу

**3. Сборка и пуш по тегу.** Тег `v*` собирает образ и кладёт его в Docker Hub с тем же тегом. На пуш ветки сборки нет

**4. Секреты.** Токен Docker Hub и SSH-ключ лежат в Secrets, в коде и в логах их нет. Всё несекретное лежит в Variables

**5. Сервер без сборки.** В `docker-compose.yml` на сервере у приложения `image`, `build` нет. Healthcheck у приложения есть, деплой идёт с `--wait`

**6. Сломанный релиз.** Выпусти версию, которая не проходит healthcheck: например, приложение ходит в базу с неправильным именем хоста. Пайплайн должен покраснеть на деплое

**7. Откат.** Верни прошлую версию кнопкой Run workflow и покажи `/health` с прошлой версией

**8. Флоу проекта.** Опиши в README проекта: какие ветки, что запускает релиз, как делается хотфикс и почему такой флоу подходит твоей команде. Отдельно ответь, при каком размере команды ты бы его поменял и на какой

Результат: ссылки на прогоны в Actions (зелёный релиз, красный линт, красный деплой, откат), вывод `curl /health` до и после отката, раздел про флоу в README проекта
